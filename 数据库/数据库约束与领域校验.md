# 数据库约束与领域校验

## 问题

建表时应该放很多 `CHECK` 吗？哪些规则属于数据库，哪些属于领域代码？如果业务以后增加角色或状态，数据库约束会不会变成负担？

## 回答

### 核心结论

1. 数据库保护数据形状和稳定不变量，领域代码保护业务行为。
2. 判断规则放哪一层，看它是否需要上下文、是否会频繁变化，以及违反后是否破坏数据本身。
3. 同一规则在 API、领域代码和数据库出现，不一定重复；它们服务不同故障场景。

### 1. 三层职责

| 层次 | 主要职责 | 典型规则 |
|---|---|---|
| API 层 | 解析和验证外部输入 | 必填字段、字符串长度、UUID 格式、分页大小 |
| 领域层 | 执行和授权业务行为 | 谁能开始工单、状态如何转换、引用是否同租户 |
| 数据库层 | 拒绝结构错误的数据 | 主键、唯一索引、非空、类型、基础取值范围 |

API 校验和数据库约束不能互相替代。

API 校验负责给用户清楚的错误信息，并尽早拒绝无效请求。数据库约束负责最后一道数据完整性，即使应用有 bug、人工执行 SQL 或其他消费者写库，也不能写入破坏数据语义的值。

### 2. 适合数据库的规则

数据库适合处理满足以下条件的规则：

- 只看当前一行或唯一性就能判断
- 规则稳定，不会随角色或流程频繁变化
- 违反后整张表的数据语义会损坏
- 多个写入入口都可能接触这张表

例如：

- `PRIMARY KEY`
- 业务唯一字段的 `UNIQUE KEY`
- `NOT NULL`
- 字段类型和长度
- 状态值只能属于闭集合
- 版本号必须大于等于 1
- `ASSIGNED` 状态必须有当前负责人

唯一性必须由数据库兜底。应用层的“先查再插”存在竞态：两个请求可以同时查到“不存在”，然后同时插入。只有数据库唯一索引能保证最终只有一条成功。

### 3. 适合领域代码的规则

领域代码负责需要上下文的行为：

- 谁有权执行命令
- 当前用户是不是被指派的技术员
- 更新前后的状态是否允许转换
- 客户、设备、用户是否属于同一租户
- 设备是否属于工单中的客户
- 状态更新和审计事件是否必须原子提交
- 终态是否允许新增评论

例如“只有当前技术员才能开始工单”。这条规则需要知道：

1. 当前登录用户是谁
2. 用户拥有什么角色
3. 工单当前指派给谁
4. 工单当前是什么状态
5. 当前租户是什么

数据库普通 `CHECK` 无法读取当前登录用户，也看不到更新前的状态。即使使用触发器补齐上下文，也会形成难以测试和迁移的隐式业务逻辑。

如果以后允许“区域主管”也开始工单，只需调整领域授权策略，不应为了一个权限变化修改表结构。

### 4. 为什么要防止规则源漂移

把完整状态机写成多层数据库 `CHECK`，会形成两个规则源：

```text
Java 状态机：OPEN -> ASSIGNED
MySQL CHECK：也维护一份 OPEN -> ASSIGNED
```

任何状态变化都要同时修改 Java 代码、测试和数据库迁移。两处稍有不同，就会出现“领域代码允许但数据库拒绝”或相反的情况。

因此 FixFlow 的选择是：

- 状态机和命令权限由领域代码作为唯一来源
- 数据库只检查状态值是否合法、状态与当前负责人是否自洽
- 审计事件版本由数据库唯一索引保护
- 完整的命令到状态转换由领域状态机和测试保护

### 5. FixFlow 的约束收敛

`work_order` 保留两个业务检查：

1. 优先级、状态和聚合版本的数据形状
2. 状态与当前负责人是否自洽

`work_order_event` 保留三个业务检查：

1. 聚合版本大于等于 1
2. 命令类型合法
3. 前后状态值合法

删除“`CREATE` 事件必须没有旧状态”的数据库检查。这个规则属于事件构造行为，放在领域代码和测试中，避免在数据库再维护一份事件语义。

### 6. 重复校验是否浪费

不一定。三层校验处理的是不同问题：

| 场景 | 依靠哪层 |
|---|---|
| 用户输入了 300 字符的标题 | API 返回明确校验错误 |
| 技术员尝试操作别人的工单 | 领域授权拒绝 |
| 两个请求同时创建同一公开 ID | 数据库唯一索引保证仅一个成功 |
| 人工 SQL 写入未知状态 | 数据库状态检查拒绝 |

真正应该避免的是在多个地方维护同一套复杂业务流程，而不是拒绝所有重复的简单数据校验。

## 常见误解

| 误解 | 纠正 |
|---|---|
| 业务规则都应该放到数据库 | 数据库无法可靠获得用户身份、更新前状态和跨服务上下文 |
| 代码已经校验，所以数据库唯一索引没必要 | 应用校验存在并发竞态，唯一索引才是最终保证 |
| 把所有规则都放数据库最安全 | 复杂 `CHECK` 和触发器会让业务规则难测试、难演进 |
| 把所有规则都放代码最简单 | 应用绕过、人工订正或并发写入可能产生脏数据 |
| 约束数量越多，设计越严谨 | 约束应覆盖真实不变量；重复业务规则只会增加漂移 |

## 相关问题

- 为什么业务唯一字段必须建唯一索引？ -> 应用层先查再插无法抵抗并发竞态。
- 为什么状态转换不写进 `CHECK`？ -> 普通 `CHECK` 看不到更新前后的状态，完整状态机应由领域代码和测试维护。
- 新增角色为什么要尽量不改表？ -> 角色权限是策略，不是数据形状；策略变化不应自动升级为数据库迁移。
- 数据库外键为什么放在应用层维护？ -> 当前项目遵循《阿里巴巴 Java 开发手册》的禁用外键规约，通过事务、校验和测试补足。
