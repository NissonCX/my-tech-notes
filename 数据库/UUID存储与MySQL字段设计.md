# UUID 存储与 MySQL 字段设计

## 问题

UUID 是 128 位值，为什么数据库里常用字符串类型存储？`BIGINT` 只有 64 位，为什么还能和 UUID 同时出现？《阿里巴巴 Java 开发手册》又怎样约束这些选择？

## 回答

### 核心结论

1. UUID 是固定的 128 位值；规范文本表示固定为 36 个字符。
2. `BIGINT` 和 UUID 承担不同职责：前者是数据库内部主键，后者是对外公开标识。
3. 《阿里巴巴 Java 开发手册（黄山版）》对长度固定的字符串要求使用 `CHAR`，所以公开 UUID 文本使用 `CHAR(36)`。

### 1. 两个 ID，各做一件事

FixFlow 采用两个标识：

| 职责 | 字段 | MySQL 类型 | 是否对外暴露 |
|---|---|---|---:|
| 数据库主键、关联、索引 | `id` | `BIGINT UNSIGNED` | 否 |
| API、URL 中的资源标识 | `public_id` | `CHAR(36)` | 是 |

`BIGINT UNSIGNED` 是 64 位。UUID 是 128 位。两者不是同一种 ID，也不存在把一个 128 位 UUID“装进”64 位整数的问题。

内部主键使用自增整数，能让 InnoDB 的主键索引按顺序增长。公开 UUID 不参与主键和连接关系，表之间仍使用内部整数 ID。

### 2. UUID 的规范文本表示

UUID 本身是 128 位值，通常写成：

```text
8 位 - 4 位 - 4 位 - 4 位 - 12 位
```

合计 36 个字符，其中：

- 32 个十六进制字符
- 4 个连字符

所以“UUID 文本表示长度固定”不等于“UUID 本质上就是字符串”。它首先是一个 128 位标识值，36 字符是规范编码。

Java 可以直接使用 `UUID.randomUUID()` 生成 UUID 对象，再通过 `toString()` 得到规范文本。

### 3. MySQL 的三种常见存储方式

| 类型 | 表示 | 空间特征 | 主要代价 |
|---|---|---|---|
| `CHAR(36)` | 规范 UUID 文本 | 固定 36 字符 | 比二进制表示更大 |
| `VARCHAR(36)` | 规范 UUID 文本 | 约 36 字符加长度信息 | 长度固定时没有利用类型语义 |
| `BINARY(16)` | 原始 128 位值 | 固定 16 字节 | 查询、日志、数据同步都需要转换 |

《阿里巴巴 Java 开发手册（黄山版）》MySQL 建表规约第 7 条是【强制】规则：

> 如果存储的字符串长度几乎相等，使用 char 定长字符串类型。

因此当前 FixFlow 选择 `CHAR(36)`。`BINARY(16)` 不是错误方案，但它引入额外转换成本，只有出现明确的容量或索引压力时才值得考虑。

公开 UUID 还必须建立唯一索引。手册索引规约第 1 条规定：业务上具有唯一特性的字段，即使是组合字段，也必须建立唯一索引。不能只依靠应用层“先查再插”。

### 4. 为什么公司里经常看到 VARCHAR

常见并不意味着 `VARCHAR` 一定更优。生产系统常选文本 UUID，主要因为它降低了协作成本：

- `SELECT`、日志和接口返回中的值可直接阅读
- ORM、CDC、数据仓库和导入导出工具默认按字符串处理
- 公开 ID 往往不参与连接查询，额外空间在中低数据量下不是主要矛盾
- 团队已经形成统一约定，转换错误比节省少量空间更昂贵

另外，很多公司的 `VARCHAR` 字段并不是 UUID，而是 `ORD-20261024-xxx`、`USER-xxx` 这类本来就变长、带业务前缀的标识。

选择类型时要区分三件事：

1. 标识值的语义是什么
2. 规范文本编码是否固定
3. 当前系统的瓶颈是否真的是这几个字节

### 5. 手册怎样进入设计流程

《阿里巴巴 Java 开发手册（黄山版）》将规则分为三类：

| 等级 | 执行方式 |
|---|---|
| 【强制】 | 硬性门槛，违反时不能进入下一步 |
| 【推荐】 | 默认采用；偏离时用 ADR 记录原因和风险 |
| 【参考】 | 在设计评审中考虑，不机械套用 |

FixFlow 固定使用黄山版 v1.7.1（2022-02-03），避免不同人凭记忆引用不同版本。

当前已经受手册直接约束的建表规则包括：

- 每张表必须有 `id`、`create_time`、`update_time`
- `id` 使用 `BIGINT UNSIGNED`，单表自增
- 业务数据使用逻辑删除 `is_deleted`
- 表名小写、单数、避免保留字
- 不创建数据库外键和级联
- 索引按 `pk_`、`uk_`、`idx_` 命名
- 金额使用 `DECIMAL`
- 多表 SQL 不 Join 超过三张表

## 常见误解

| 误解 | 纠正 |
|---|---|
| `BIGINT` 是 64 位，所以不能存 UUID | 内部主键和公开 UUID 是两个字段，各自承担不同职责 |
| UUID 是 128 位，所以必须用 `BINARY(16)` | 二进制更紧凑，但文本表示也是合法选择；应按可读性、工具兼容和实际压力决策 |
| 公司常用 `VARCHAR`，所以 `VARCHAR` 是最佳实践 | 常见常来自生态兼容和团队约定，不等于所有场景的最优类型 |
| `VARCHAR(36)` 和 `CHAR(36)` 没有区别 | UUID 文本定长，`CHAR` 更直接表达约束；手册对此有强制要求 |
| UUID 不容易猜，所以可以替代权限检查 | UUID 只是公开定位符，授权仍要检查租户、角色和对象归属 |

## 相关问题

- UUID v4 的随机位如何分配？ -> 122 位随机数据，4 位版本标识，2 位变体标识。
- 为什么不让随机 UUID 直接做 InnoDB 主键？ -> 主键索引按主键顺序组织数据，随机值会造成随机插入和页分裂。
- `BINARY(16)` 什么时候值得用？ -> 表或索引很大、UUID 被大量复制到索引中，并且已经测量到存储或 I/O 压力。
- 为什么不直接使用物理外键？ -> 当前明确遵循手册规约，由应用事务维护关系完整性，并用集成测试和核对任务补足。
