# 大模型推理与 KV Cache 基础

日期：2026-10-01
标签：大模型, KV Cache, Transformer, Prefix Cache, 推理优化, MaaS

## 问题

起因是在使用 DSH（DeepSeek Harness）时，看到界面上显示"缓存命中率"，于是想系统性地搞清楚：

1. 缓存命中到底是怎么"命中"的？KV Cache 到底是怎么工作的？
2. K 和 V 实际代表什么？是什么形态？当前 token 的 Query 又是什么？
3. Prefill 和 Decode 分别是什么？DSH 那个命中率指的是哪个阶段？
4. 用户每次的 Prompt 都不一样，Prefix Cache 凭什么能命中 90%+？
5. 命中率公式里的"写入（cache write）"是什么？为什么 DeepSeek 那里是 0？
6. 位置表是怎么来的？为什么加了位置信息就能区分语序？
7. "32 层"是什么？为什么每层都要存一套 K/V？
8. 为什么 decode 是 memory-bound？批处理为什么能提高吞吐？

## 回答

### 0. 起点：DSH 面板上那个百分比的精确口径

DSH 界面上显示为 `Cache hit {percent}%`（`stats.cacheHit`），实现在 `@deepseek-ai/dsh-client-ui-chat` 的 `StatsPills.tsx` / `token-format.ts`：

```
会话累计命中率 = cacheReadTokens / (uncachedInputTokens + cacheReadTokens + cacheWriteTokens)
```

用本机当前会话的真实日志（`~/.dsh/sessions/...`）验证：

| step | 未缓存输入 | 缓存命中 | 输出 | 该次 total |
|---:|---:|---:|---:|---:|
| 1 | 10,797 | **0** | 1,018 | 11,815 |
| 2 | 20,537 | 11,776 | 355 | 32,668 |
| 3 | 1,711 | 32,640 | 410 | 34,761 |
| 4 | 2,703 | 34,688 | 353 | 37,744 |
| 11 | 155 | 48,128 | 294 | 48,577 |

会话累计：`381,312 / (44,073 + 381,312 + 0) = 89.64%`

**三个关键口径事实：**

- **三个桶互斥**：`inputTokens` 是*未缓存*输入，缓存部分单独报。DeepSeek 的 `prompt_tokens` 是含命中的总数，适配器必须把命中部分减出去（见 `@deepseek-ai/dsh-llm` 的 `TokenUsage` 注释）。
- **分母只有 prompt 侧**，不含输出 token。含 `cacheWrite` 是为了兼容 Anthropic 系（单独计费缓存写入）；DeepSeek 不上报该字段，所以恒为 0——但**不代表没有写入发生**。
- **它是按 token 加权的会话累计值**，不是每步百分比的算术平均。冷启动的 10,797 个 miss 会一直拖累它。

另外，`formatCacheHitPercent` 有一条诚实规则：**当四舍五入会把部分命中显示成 100% 时，自动增加小数位**，避免"99.6% 显示为 100%"。

**观察到的规律（重要证据）：** 每一步的 `cacheRead` 都约等于**上一步的 total**，且差值为 27~128 个 token（恒为正）：

```
step3 命中 32,640  ≈  step2 total 32,668（差 28）
step4 命中 34,688  ≈  step3 total 34,761（差 73）
```

说明：**命中的单位是"前缀"，而且连模型自己生成的内容也算在内**；那个几十 token 的缺口就是"缓存前缀单元"的量化边界（DeepSeek 官方文档称之为缓存前缀单元，受 Sliding Window Attention 影响）。

参考：[上下文硬盘缓存 | DeepSeek API Docs](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)

### 1. 一条链，从文本到输出

```
文本 "缓存命中率"
  │ ① 分词 tokenization
  ▼
["缓存", "命中", "率"]
  │ ② 查词表 tokenizer → token id
  ▼
[38291, 7712, 445]
  │ ③ 嵌入查表 embedding lookup
  ▼
[[0.2,-1.1,...], [0.9,0.3,...], [...]]    每个 4096 维（= 模型宽度 hidden size / d_model）
  │ ④ 加位置信息 positional encoding
  ▼
h⁰  初始隐藏状态 initial hidden state
  │
  │ ⑤ 重复 32 次（32 个 Transformer layer）：
  │      自注意力子层 self-attention sublayer
  │         └─ h = h + 注意力输出
  │      前馈子层 feed-forward sublayer (FFN)
  │         └─ h = h + MLP 输出
  ▼
h³²  最终隐藏状态 final hidden state（= h⁰ + Δ₁ + … + Δ₃₂，残差流 residual stream）
  │ ⑥ 输出投影 output projection
  ▼
logits（词表上每个词的分数）
  │ ⑦ softmax → 概率 → ⑧ 采样 sampling
  ▼
下一个 token
```

#### 1.1 分词与词表

- **词表（vocabulary）不是模型学出来的权重，而是分词器（tokenizer，BPE 等）的产物**，训练前定好、之后冻结，通常 5 万~15 万条。
- 词表条目是**高频片段**而非严格的"词"：罕见词会被拆开（`ChatGPT` → `Chat`+`G`+`PT`），生僻字可能退化到字节级。所以**任何输入都能被编码**。
- 中文常比英文费 token，所以按 token 计费会体现中英文差异。

#### 1.2 嵌入与"维度"

- **嵌入（embedding）**：拿 token id 去 `[词表大小 × 4096]` 的矩阵里查**一整行**，得到 4096 个浮点数。它是这个词在语义空间里的**坐标**，不是相似度（相似度是有了坐标之后才算的）。
- **维度（dimension）= 这串数字有多长**。4096 维 = 4096 个数。它是模型的**宽度**（hidden size / d_model）；层数则是**深度**。
- 为什么不用 3 维：一个 token 要同时携带成千上万个独立特征，且这些"特征轴"是训练自己分配出来的，没有人类名字。

#### 1.3 位置编码：为什么加了它就能区分语序

**问题**：注意力是**对集合做加权求和**，本身对顺序无感。反例（记住最后一个 token 相同的构造）：

```
句子 A:  猫  狗  追      （猫追狗）
句子 B:  狗  猫  追      （狗追猫）
```

"追"在两句里 Q 完全相同，能看到的 K/V 集合也完全相同 → **加权结果一字不差 → 模型在数学上不可能区分这两句话**。

（因果掩码只能提供"我的前缀有多长"这种粗粒度信息，无法表达集合内部谁先谁后。）

**解法：打破对称性。** 让每个 token 的向量本身带上位置差异：

$$h^0_i = \text{Emb}[w_i] + \text{Pos}[i]$$

- **两张表互相独立**，唯一交集是**列数相同（都是 4096）**，所以能逐位相加。
- 序号**选出的是整行**（4096 个数），不是"某一个维度"。
- **同一个座位，谁坐都加同一行**：猫在第 3 位、狗在第 3 位，加的都是 `Pos[3]`。

**为什么要两张表（第一性原理）**：若合并成一张表，需要 `50000 × 4096 = 2 亿行`，比整个模型还大且绝大多数格子用不到。拆开后 5 万行 + 4096 行，还获得了组合泛化能力。**这是"解耦"的价值。**

**位置表的来源**：① 可学习（随机初始化 + 训练调整，是模型参数）；② 用正弦/余弦公式生成（不占参数）。

**RoPE（旋转位置编码）**：把 Q/K 里成对的数看作二维点，按位置旋转 `m·θ`。因为旋转后的点积**只取决于角度差 (m−n)·θ**，所以天然表达**相对距离**，且不需要位置表、外推更好。

**关键认知**：位置编码**不告诉模型语序的含义**，它只提供"可区分性"：

$$\text{可区分（位置编码给）} + \text{可学习（训练给）} = \text{学会语序}$$

若两个不同语序产生完全相同的内部状态，模型**在数学上被迫输出相同结果**，无论怎么调参都学不会——不是"学得差"，是"不可能"。

#### 1.4 自注意力：Q / K / V

同一个输入 `h`，乘三个不同的矩阵：

```
Q = h × W_Q   ← 检索意图：我要找什么
K = h × W_K   ← 可被匹配的特征：我是什么
V = h × W_V   ← 可被取走的内容：我带着什么

① 打分：score = Q · Kᵀ
② 归一化：权重 = softmax(score)
③ 加权求和：o = Σ 权重 × V
```

**四条不能串的事实：**

- K/V **只由 token 自己和位置决定**，与谁的 Q 来问无关，与未来无关。
- 打分算出来的是**注意力输出 o（上下文向量）**，**既不是 K 也不是 V**。
- Q/K/V **不产生输出**，它们只负责让信息在 token 之间流动；输出来自最终的 `h` 乘输出投影矩阵。
- **每层都有自己的一套 Q/K/V**（因为每层的输入 `h` 不同）。

**手算示例**（维度缩到 2 便于核对，`Q_追 = [1,0]`）：

| 历史 token | K | V | Q·K |
|---|---|---|---|
| 小 | [1,0] | [1,0] | 1 |
| 猫 | [0,1] | [0,1] | 0 |
| 在 | [1,1] | [1,1] | 1 |

`softmax([1,0,1]) ≈ [0.42, 0.16, 0.42]`

```
o = 0.42×[1,0] + 0.16×[0,1] + 0.42×[1,1]
  = [0.84, 0.58]        ← 这才是注意力输出，不是 K 也不是 V
```

#### 1.5 因果掩码 causal mask

```
     看 →   猫   狗   追
猫          ✓    ✗    ✗
狗          ✓    ✓    ✗
追          ✓    ✓    ✓
```

别名：**masked self-attention**（原论文叫法）、**look-ahead mask**、**lower-triangular mask**（下三角）。性质本身叫**自回归 autoregressive**。

它的作用是整件事的**法律依据**：老 token 看不见未来 → 它的 K/V 永不改变 → 可被缓存。

#### 1.6 为什么要 32 层

一层 = 自注意力子层（横向交换信息）+ 前馈子层（纵向加工），两个都用残差连接包裹。

**必须多层的四个理由：**

1. **一跳不够**：一层只能建立一次关联，而语言关系需要多跳（"它→书"、"需要→李四"）。
2. **信息传播需要层数**：让信息在 token 间传播 k 跳，至少需要 k 层。
3. **非线性需要堆叠**：没有激活函数，多层线性叠加仍等于一层线性。
4. **参数容量**：每层权重不共享，层数直接决定参数总量。

层数是**超参数**（12 / 32 / 96…），训练前定、训练后冻结。**层数管深度、维度管宽度**，一起决定模型规模（参数量大致按 `层数 × 维度²` 增长）。

### 2. 为什么 K/V 可以被缓存（第一性原理五步）

1. 推理是**串行**的（自回归）：第 50 个字取决于前 49 个字，而它们此刻还不存在。
2. 注意力是**对集合的加权求和**，本身不管顺序。
3. **因果掩码**限制了"谁只能看谁"→ 老 token 看不见未来。
4. 因此老 token 的 K/V **只由它自己和位置决定，永不随新 token 改变**。
5. 不变就能存 → **KV Cache**。

**推论**：只有 decoder-only 结构才配拥有 KV Cache。BERT 那类双向注意力（bidirectional attention）里，新 token 到来会改变已有 token 的表示，缓存立即失效。

---

### 3. 层与层：垂直传 h，水平沉 K/V

**这是最容易卡住的一点。"32 层加工 h" 和 "32 层各存一套 K/V" 不是两件事，而是同一次计算的两个出口。**

把一层放大：

```
第 k 层
  输入：h^{k-1}
  ┌────────────────────────────────────────────┐
  │ ① 投影：Q = h^{k-1}×W_Q, K = h^{k-1}×W_K, V = h^{k-1}×W_V
  │ ② 把 K、V 存进【第 k 层档案】            ★ 沉淀
  │ ③ 注意力：我的 Q 比对【第 k 层档案里所有历史 K】→ 混合 V → o
  │ ④ h^k = h^{k-1} + o
  │ ⑤ h^k = h^k + MLP(h^k)
  └────────────────────────────────────────────┘
        │                          │
   往上走：h^k                 留在原地：K_k, V_k
   交给第 k+1 层               供未来每一步查阅
```

**一次计算，两个出口**：一份流上去（h），一份留下来（K/V）。

```
        ┌─────────┐   h¹    ┌─────────┐   h²    ┌─────────┐
        │ 第 1 层  │ ──────▶ │ 第 2 层  │ ──────▶ │ 第 3 层  │
        └────┬────┘         └────┬────┘         └────┬────┘
             │                   │                   │
           K₁V₁                K₂V₂                K₃V₃
             ▼                   ▼                   ▼
        【1号档案】          【2号档案】          【3号档案】
             ▲                   ▲                   ▲
             └──── 每一步 decode 都回来翻阅各自的档案 ────┘
```

**两组必须分清的性质：**

| | h（隐藏状态） | K/V |
|---|---|---|
| 性质 | **流动** | **沉淀** |
| 会不会被改写 | ✅ 每层改写一次 | ❌ 算出后永久冻结 |
| 谁用它 | 下一层作为输入 | 只有它自己那一层用 |
| 新 token 来了 | 走一遍新流程 | **在末尾追加一行** |

**为什么 32 本账都不能删：**

- 层与层之间**只传 h，不传 K/V**（第 k 层用的是由 `h^{k-1}` 现算出的、第 k 层自己的 K/V）。
- 但每个新 token 走到第 k 层时，都要重新问一次"**历史 token 在我这一层的 K/V 是什么**"。
- 所以中间少存任何一层 → 那一层就得把整段 prompt 从头重跑。**32 套要么全有，要么全无。**

**可以删的方向只有"位置"（不是"层"）**：丢掉最老的 token 的账 = **KV 驱逐 KV eviction / 滑动窗口注意力 sliding window attention**，省显存但永久丢失那部分上下文。

### 4. Prefill 与 Decode

| | Prefill（预填充） | Decode（解码） |
|---|---|---|
| 一次处理几个 token | **N 个（全部并行）** | **1 个** |
| 爬几层 | 32 层 | 32 层 |
| 瓶颈 | 计算受限 **compute-bound** | 访存受限 **memory-bound** |
| 决定什么指标 | **TTFT**（首 token 延迟） | **TPOT**（每输出 token 时间）、吞吐 |
| 为什么是这个数量 | 所有 token **都已存在** | 未来的 token **还没被生成出来** |

**依赖关系**：**层内并行，层间串行。**

- 同一层内部：10 个 token 的 K/V 可以在同一瞬间全部算出（因为各自的 `h^{k-1}` 都已到手）。
- 层与层之间：第 2 层必须等第 1 层全部完成 → **同步点 synchronization point / barrier**。

因果掩码限制的是"每个 Q 能看到哪些 K"，**不是**"能不能同时算"。

**为什么必须 32 套：** 每一步 decode，每一层都要重新追问一次历史 K/V——因为每一层都要做自己那次注意力。少存一层，它上面的所有层都得从零重跑。

### 5. 跨请求：Prefix Cache

**关键区分：这是两件不同的事。**

| | 场景 A：请求内 decode | 场景 B：新的模型调用 |
|---|---|---|
| 复用谁的账 | 本次请求自己刚留下的 | **之前某次请求**留在缓存池里的 |
| 需要匹配吗 | 不需要，必然命中 | **需要，按最长公共前缀** |
| 可能失败吗 | 不可能 | 可能（尽力而为） |
| 机制名 | 请求内 KV Cache | **Prefix Cache** |

**在 DSH 里，"一轮对话"其实由很多次独立的 API 调用组成。** 每次调用都是一个"新 prompt"，但它的前缀和上次几乎完全相同：

```
第 1 次调用： [系统提示 + 工具定义 + 用户问题]                          10,797 token
第 2 次调用： [系统提示 + 工具定义 + 用户问题 + 我的回答 + 工具结果 + 新话]
              └──────────── 与上次完全相同（11,776 token）────────────┘ └新增┘
```

**所以"用户 prompt 每次都不同"是个错觉**：变化的只有末尾一小截，前面躺着几万 token 的稳定前缀。**不是"两个人问了相似的问题"，而是"同一本书，每次只在末尾追加一行"。**

数据佐证：step 3 命中 32,640 / 新增 1,711 → **该轮 95% 是读缓存**；step 11 命中 48,128 / 新增 155 → **99.7%**。**对话越长，命中占比越高**（分子线性增长，分母几乎不增）。

**核心性质：追加便宜，修改昂贵。** 匹配规则是**严格的最长公共前缀**，第一个不同的 token 就是终点。改开头一个字符 → 从那个点起**每一层的后面全部失配**（因为 `h_t` 依赖第 1~t 个 token，因果链一断全废）。所以是**阶跃函数**，不是渐变。

**DSH 里为"保住前缀"做的三层设计：**

| 变化的东西 | 天真的做法 | DSH 的做法 | 后果 |
|---|---|---|---|
| 技能目录成员变化 | 改写系统提示 | **末尾追加完整替换目录**（`durable user-role message`） | ✅ 前缀保住 |
| 系统提示词内容变化 | 改写开头 | **`systemPromptUpdate: in-history`**：追加到缓存历史之后 | ✅ 历史前缀保住 |
| 工具 schema 变化 | — | 无法回避（schema 在请求头部） | ❌ 从头失配 |
| 用户新说的话 | — | 天然追加在末尾 | ✅ 永远廉价 |

### 6. 显存公式：KV Cache 有多大

```
总字节 = 位置数 × 每层每位置的 K/V 维度 × 2(K和V) × 层数 × 每数字节
```

代入（5 万 token、GQA 配置、fp16）：

| 步骤 | 算式 | 中间结果 |
|---|---|---|
| 每层每 token 的 K/V 维度 | — | **1024** = 8 个 KV 头 × 128 维 |
| 5 万 token 在一层里的 K | 50000 × 1024 | 51,200,000 个数 |
| 补上 V | × 2 | 102,400,000 个数 |
| 32 层 | × 32 | 3,276,800,000 个数 |
| fp16 每数 2 字节 | × 2 | **6,553,600,000 字节 ≈ 6.1 GiB** |

**三种注意力方案的对比（同样 5 万 token）：**

| 方案 | Q 头数 | K/V 头数 | K/V 维度 | 缓存大小 | 相对 |
|---|---:|---:|---:|---:|---:|
| **MHA** | 32 | 32 | 4096 | 26.2 GB | 32× |
| **GQA** | 32 | 8 | 1024 | **6.5 GB** | 8× |
| **MQA** | 32 | 1 | 128 | 0.8 GB | 1× |

**关键洞察**：Q 是"问题"，K/V 是"档案"。**没人规定 K/V 必须和 Q 一样多**——档案可以少几本让大家共用。这就是 GQA（4 个 Q 头共用 1 份 K/V）和 MQA 的由来。

**对 MaaS 的直接含义**（80 GB 卡，7B 模型 fp16 权重约 14 GB，留给 KV 约 60 GB）：

| 每请求上下文 | 单请求 KV | 能同时服务 |
|---|---:|---:|
| 5 万 token | 6.5 GB | 约 9 个 |
| 1 万 token | 1.3 GB | 约 45 个 |

**这就是"并发数被显存卡死"的具体含义。**

### 7. 性能视角：compute-bound vs memory-bound

| 中文 | English | 定义 |
|---|---|---|
| **访存受限** | **memory-bound** | 瓶颈在数据搬运速度 |
| **计算受限** | **compute-bound** | 瓶颈在计算能力 |
| **显存带宽** | **memory bandwidth** | 每秒能从显存搬多少字节 |
| **算术强度** | **arithmetic intensity** | 每搬 1 字节能做多少次浮点运算 |

**注意区分容量与带宽（两个独立瓶颈）：**

| | 决定什么 | 优化手段 |
|---|---|---|
| 显存**容量** capacity | 能同时服务几个请求 | GQA / MLA / 量化 / KV 驱逐 |
| 显存**带宽** bandwidth | 生成速度（tokens/s） | 批处理 |

**算一笔账**（高端卡量级：带宽约 3 TB/s，算力约 1000 TFLOPS fp16）：

```
decode 一个 token 要搬：权重 ~14 GB + KV ~6 GB = ~20 GB
                     要算：~14 GFLOPs

搬 20 GB：    20 ÷ 3000 GB/s ≈ 6 毫秒
算 14 GFLOPs：14 ÷ 1000     ≈ 0.014 毫秒
                            ─────────
                    搬数据比算数慢 400 多倍
```

**每个 token 的 6 毫秒里，5.99 毫秒在等数据。** 这就是 memory-bound 的实感：算力几乎全程闲着。

### 8. 批处理与服务端架构

**batching 的本质**：模型权重只有一份，让"搬一次权重"服务更多 token。

| 配置（4K 上下文） | 要搬 | 产出 | 摊到每 token |
|---|---|---:|---:|
| batch = 1 | 14 GB 权重 + 0.5 GB KV | 1 个 | **14.5 GB** |
| batch = 32 | 14 GB 权重 + 16 GB KV | 32 个 | **0.95 GB** |

**吞吐提升十几倍，而单请求延迟几乎不变**——因为在 memory-bound 世界里，权重读取这个固定成本被摊薄了。

**必须搞清的一点：batch 里的"多"是"多个请求"，不是"同一请求的多个 token"。**

| | 能否批 | 原因 |
|---|---|---|
| 同一请求的多个 token | ❌ | token 之间有前后依赖（自回归） |
| 不同请求之间 | ✅ | 互不依赖，且共用同一份权重 |

**服务端架构（那个"中间层"的正式名字）：**

```
  用户 A ─┐
  用户 B ─┼──▶ API 网关 ──▶ 调度器 ──▶ 模型实例（权重常驻显存）
  用户 C ─┘   gateway     scheduler      │
                                         ├── KV 管理器：A/B/C 各自账本
                                         ▼
                                一次算完，按请求拆开返回
```

**"搬权重"要分三个层次，不能混：**

| 层次 | 搬什么 | 频率 |
|---|---|---|
| ① 磁盘 → 显存 | 模型权重 | **一次**（模型加载 model loading） |
| ② 显存 → 计算单元 | 权重 | **每一步**（weight read） |
| ③ 显存 → 计算单元 | 各请求 KV | **每一步**（KV cache read） |

**②③ 是瓶颈，且发生在 HBM（显存）与 SM（流式多处理器）之间**，不是在网络上搬。

**硬件角色分配：**

| 角色 | 谁 |
|---|---|
| 存放全部数据 | **HBM**（高带宽显存） |
| 真正做运算 | SM 里的运算单元 |
| 临时放"正在算的那一小块" | **SRAM / 寄存器**（片上存储，仅几百 KB/SM） |
| 决定搬什么 | 编译器 + kernel 指令 |
| 实际搬运 | 显存控制器（硬件自动） |

**关键：不是"把权重交给 SM"，而是"流过去"。** 显存 80 GB vs 片上存储几十 MB，差约 1000 倍以上，装不下。数据是**分块（tiling）流经** SM 的。

**批处理的隔开问题**：batch 内不同请求**绝不能串扰（cross-contamination）**。工程上不只是加 mask——因为各请求序列长度不同，padding 会浪费算力，所以用 **varlen attention / sequence packing**（`cu_seqlens` 标出每段边界）或 **block table**。

**进阶机制：**

| 中文 | English | 作用 |
|---|---|---|
| 连续批处理 | **continuous batching** | 每步重组 batch，谁做完谁走，新请求随时进来 |
| 分块预填充 | **chunked prefill** | 长 prefill 切块，与 decode 混跑 |
| 预填充-解码分离 | **PD disaggregation** | prefill 与 decode 分别部署，各跑最优配置 |

### 9. 常见误解清单（本日踩过的坑）

| 误解 | 纠正 |
|---|---|
| "KV Cache 省的是算下一个 token 的 K/V" | 省的是**把历史 token 的 K/V 重算一遍**；历史 K/V 一生只算一次 |
| "打分得到的是 K 和 V" | 打分得到的是**注意力输出 o**，K/V 是输入不是输出 |
| "下一个 token 决定了它的 Q" | 顺序反了：**当前位置的 Q 决定下一个 token** |
| "只缓存上一层就够，前面的可以删" | 层与层之间不传 K/V；**每层都要被未来的每一步重访** |
| "K/V 会随新 token 修改" | K/V **只追加，从不修改**——这正是可缓存、可共享的前提 |
| "位置编码让模型理解语序" | 它只提供**可区分性**；"理解"是训练给的 |
| "位置映射到某一个维度" | 序号选出的是**整行**，不是某一维 |
| "搬权重是从磁盘搬到显存" | 那是模型加载（一次）；每步的搬运是 **HBM → SM** |
| "把权重交给 SM" | SM 装不下，数据是**流过去**的 |
| "batch 是把同一请求的多个 token 一起算" | 是**多个不同请求**各算 1 个 token |
| "KV Cache 占的是显存带宽" | 应分开说：**占容量（决定并发），吃带宽（决定速度）** |

## 相关问题

- **为什么 DeepSeek 的 cacheWrite 总是 0？** → DeepSeek 不单独上报/计费缓存写入，写入成本打包进了 miss 的价格；Anthropic 系则单独上报 `cache_creation_input_tokens`，写入有溢价、读取有折扣。
- **缓存命中是 100% 保证的吗？** → 不是。官方明确"尽力而为"；还有前缀单元量化边界、闲置几小时到几天后过期、缓存构建耗时（秒级）等偏差。
- **命中缓存会改变输出的随机性吗？** → 不会。缓存只匹配**输入前缀**，输出仍由推理产生，temperature 等照常生效，效果与不使用缓存相同。
- **为什么改了 prompt 中间一个字，代价和改开头一样大？** → 因为匹配是最长公共前缀，且 `h_t` 依赖第 1~t 个 token；断点之后，**每一层的后面**都要重跑。
- **GQA 让 4 个 Q 头共用 1 份 K/V，为什么不会让模型崩掉？** → 因为 Q 是"问题"、K/V 是"档案"，两者数量本来就是设计自由度；共用会损失一些表达能力，但通常是可接受的折中（MQA 更极端）。
- **MLA 是什么？** → 多头潜在注意力 multi-head latent attention。不直接存完整 K/V，只存**压缩后的潜向量 latent**，用的时候现展开。压得比 GQA 更狠、质量损失更小。（下次专题）
- **为什么位置编码可以用加法？会不会把词义搅乱？** → 4096 维空间足够大，模型会学会在不同方向上分别编码词义与位置，互不干扰。
