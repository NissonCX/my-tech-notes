# 状态机与转换表

## 问题

业务对象的状态转换应该怎样表达？为什么不能只记录“当前状态会变成什么”？用 `Map`、`Set` 还是大量 `if` 更合适？

## 回答

### 核心结论

1. 状态机描述“当前状态 + 业务命令”是否合法，以及合法后到达什么状态。
2. 一条转换可以看成有向图的一条边，命令是边上的标签。
3. FixFlow 使用 `Map<Transition, WorkOrderStatus>` 保存边到终点的映射。

### 1. 三个基本概念

以 FixFlow 工单为例：

| 概念 | 示例 | 含义 |
|---|---|---|
| 当前状态 `currentStatus` | `ASSIGNED` | 对象现在处于什么生命周期位置 |
| 业务命令 `command` | `START` | 用户希望执行什么动作 |
| 下一状态 `nextStatus` | `IN_PROGRESS` | 命令成功后的状态 |

状态机计算的是一个部分函数：

```text
nextStatus = transition(currentStatus, command)
```

不是所有输入都有结果。例如：

```text
ASSIGNED + START -> IN_PROGRESS
OPEN + START     -> 非法
```

### 2. 把状态机看成有向图

- 状态是节点
- 命令是边上的标签
- 执行转换就是沿一条合法边移动

例如：

```text
OPEN --ASSIGN--> ASSIGNED --START--> IN_PROGRESS
```

因此一条转换至少需要两个身份字段：

```text
currentStatus + command
```

这两个字段共同确定一条边。

### 3. 为什么不能只保存 `currentStatus -> nextStatus`

假设只记录：

```text
OPEN -> ASSIGNED
```

会丢失两个信息：

1. 是通过什么命令到达的
2. 同一状态下其他命令应该去哪里

例如 `OPEN` 至少有两条合法边：

```text
OPEN + ASSIGN -> ASSIGNED
OPEN + CANCEL -> CANCELLED
```

如果键只有 `OPEN`，就无法同时表达这两个不同结果。

### 4. 常见数据结构比较

| 方案 | 优点 | 局限 |
|---|---|---|
| 大量 `if` 或 `switch` | 起步直观 | 规则多后分支冗长，查询允许命令容易重复逻辑 |
| `Map<Status, Set<Command>>` | 便于查询某状态允许哪些命令 | 只知道命令合法，不知道目标状态 |
| `Map<Transition, Status>` | 同时表达边身份和目标状态 | 查询一个状态的全部命令需要扫描转换表 |

FixFlow 只有少量转换，扫描成本可以忽略，所以第三种最简单。

### 5. Java 中的具体承载

```java
private record Transition(
        WorkOrderStatus currentStatus,
        WorkOrderCommand command) {
}

private static final Map<Transition, WorkOrderStatus> TRANSITIONS;
```

`record` 自动生成 `equals()` 和 `hashCode()`，因此两个字段相同的 `Transition` 会被 Map 视为同一个键。

转换查询：

```java
WorkOrderStatus nextStatus =
        TRANSITIONS.get(new Transition(currentStatus, command));
```

- 找到值：转换合法
- 得到 `null`：转换非法

查询某状态允许的命令：

```text
扫描所有边
  -> 筛出 currentStatus 相同的边
  -> 收集 command
```

时间复杂度是 `O(E)`，其中 `E` 是转换数量。FixFlow 当前只有 11 条，不需要为这点规模增加缓存或嵌套 Map。

### 6. 为什么允许命令使用 `EnumSet`

`EnumSet` 是专用于枚举的集合实现，具有以下特点：

- 元素类型只能是同一个枚举
- 自动去重
- 枚举数量固定时实现紧凑
- 适合表达“允许的命令集合”

返回前使用 `Collections.unmodifiableSet()` 包装，避免调用者修改状态机内部创建的集合。

### 7. 状态机不负责什么

状态机只判断“当前状态 + 命令”是否合法。

它不负责：

- 当前用户是否为被指派的技术员
- 用户是否属于当前租户
- 角色是否拥有权限
- 数据库中的版本是否发生变化
- 更新工单和写事件是否同一事务

这些属于应用服务、授权策略和持久化层。状态转换合法不等于当前用户有权执行。

## 常见误解

| 误解 | 纠正 |
|---|---|
| 状态机一定要引入状态机框架 | 少量固定规则用 Map 或 switch 就足够，引入框架反而增加维护成本 |
| 保存当前状态就够了 | 还要保存命令才能判断如何转换；当前状态与命令共同决定下一条边 |
| `currentStatus -> nextStatus` 足够表达规则 | 它会丢失触发转换的命令，也无法表达同一状态的不同命令分支 |
| 状态转换合法，用户就一定可以执行 | 授权还依赖用户、角色、租户、负责人和当前数据版本 |
| `Map` 查询一定比扫描好，所以所有地方都应嵌套 Map | 应结合规则规模；当前只有 11 条边，简单结构更重要 |

## 相关问题

- 为什么 `Transition` 作为 Map 键需要 `equals()` 和 `hashCode()`？ -> Map 要通过值相等找到同一个键，`record` 自动提供这两个方法。
- 为什么不用数据库外键表达状态转换？ -> 状态转换是业务行为，不是实体引用关系，且需要知道用户、旧状态和命令。
- 为什么 `allowedCommands()` 返回集合而不是布尔值？ -> 前端和调用方需要知道当前有哪些可执行命令，而不只是某一个命令是否合法。
