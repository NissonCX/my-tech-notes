# 网络代理基础知识

## 问题

网络代理的工作原理是什么？为什么有时 `curl` 能走代理，但 `ping` 不一定能？

## 回答

### 核心结论

代理的本质是：**你不直接访问目标，而是先把流量交给另一个中间节点代你访问。**

之所以会出现“`curl` 能通、`ping` 不通”，通常不是网络坏了，而是因为：

- `curl` 常走的是 **应用层协议**，更容易被 HTTP/SOCKS 代理接管
- `ping` 用的是 **ICMP**，属于网络层，不一定会被普通代理处理

### 先看协议层次

```text
应用层：HTTP、DNS、SMTP
传输层：TCP、UDP
网络层：IP、ICMP
链路层：以太网、Wi-Fi
```

可以把它理解成：

- 应用层：你要传什么内容
- 传输层：怎么把内容送过去
- 网络层：往哪个地址发

### `ping` 和 `curl` 的区别

| 命令 | 常用协议 | 所在层次 | 常见是否被普通代理接管 |
|------|----------|----------|------------------------|
| `ping` | ICMP | 网络层 | 通常不会 |
| `curl` | HTTP/HTTPS | 应用层 | 通常可以 |

这就是为什么很多人第一次开代理时会看到：

- 浏览器能打开网页
- `curl https://example.com` 能访问
- `ping example.com` 仍然不通

这并不矛盾，因为它们根本不是同一种流量。

### 常见代理类型

| 类型 | 工作位置 | 常见可处理流量 | 特点 |
|------|----------|----------------|------|
| HTTP Proxy | 应用层 | HTTP/HTTPS | 最常见，适合网页和 API |
| SOCKS5 | 更通用的转发层 | TCP，部分实现支持 UDP | 比 HTTP 代理更通用 |
| TUN / VPN | 更靠近网络层 | 更多系统流量 | 更像“接管整张网卡路径” |

### 为什么普通代理不能天然代理 `ping`

普通 HTTP 代理的典型工作方式是：

```text
应用程序发 HTTP 请求
    ↓
代理客户端接管这个请求
    ↓
转发给代理服务器
    ↓
代理服务器再去访问目标站点
```

但 `ping` 不是 HTTP 请求，而是 ICMP 报文。很多代理客户端默认不会接管这类流量，因此系统会直接按照本机路由去发包。

### TUN 模式解决了什么

TUN 可以理解为“在系统里放了一个虚拟网卡”，让更多流量先进到代理程序里，再决定怎么转发。

它常见的效果是：

- 不只浏览器流量能走代理
- 更多 TCP/UDP 流量也能被统一接管
- 某些情况下连 `ping` 这类行为也可能表现不同

但要注意：

> 开启 TUN 不等于“任何场景下 `ping` 一定通”。是否能处理 ICMP，还取决于客户端实现、操作系统能力、服务端支持和路由策略。

### 四类方案怎么理解

| 方案 | 工作层次 | TCP | UDP | ICMP | 典型用途 |
|------|----------|-----|-----|------|----------|
| HTTP Proxy | 应用层 | 支持 | 通常不直接处理 | 不处理 | 浏览器、接口调试 |
| SOCKS5 | 传输层附近 | 支持 | 视实现而定 | 通常不直接处理 | 通用代理转发 |
| TUN | 网络层附近 | 支持 | 常支持 | 视实现而定 | 接管更多系统流量 |
| VPN | 更完整的隧道方案 | 支持 | 支持 | 常可覆盖更多情况 | 企业网络、全局隧道 |

### 一个更准确的理解方式

“开代理后为什么网页能访问”并不是因为代理让目标站点“突然解封”，而是因为：

- 你本机看到的目标不再直接是最终网站
- 你的流量先到代理服务器
- 再由代理服务器替你访问目标

对本机而言，真正直连的是“代理节点”；对目标网站而言，真正发起访问的是“代理节点”而不是你当前这台机器。

### 什么时候用哪种方式

| 需求 | 更合适的方式 |
|------|--------------|
| 只想让浏览器/命令行 HTTP 请求走代理 | HTTP Proxy |
| 希望更多程序复用同一代理 | SOCKS5 |
| 希望系统流量尽可能统一接管 | TUN |
| 希望获得更完整的网络隧道体验 | VPN |

## 深挖：系统代理 vs TUN —— 自愿与强制

> 这是上面所有内容的**底层分界线**。理解了这一条，"为什么有的程序走代理、有的不走"就不需要背了。

### 一句话区分

| | 系统代理 | TUN |
|---|---|---|
| 生效方式 | 应用**主动读**系统设置 | 内核**按路由表转发** |
| 谁决定走不走 | **应用自己**（读不读是它的自由） | **内核**（应用无从拒绝） |
| 覆盖面 | 只覆盖"守法"的应用 | 所有经过路由的 IP 流量 |
| 实际改了什么 | 一个**配置项** | **路由表 + 一张虚拟网卡** |
| 不生效的表现 | 静默直连，不报错 | 无法绕过（除非改路由） |

**关键认知**：系统代理**不是**"系统级的代理"，它只是"系统级的一个**配置项**"。

> **设了 ≠ 生效。** 系统代理是**自愿遵守**的君子协定；TUN 是**强制执行**的接管。
> 这就是为什么"我明明开了代理，某个程序还是不走"——不是配置错了，是那个程序根本没读。

### 谁会读、谁不读（macOS）

| 程序类型 | 读不读系统代理 | 读的是什么 |
|---|---|---|
| Cocoa 应用（Safari / Mail / Chrome） | ✅ 自动读 | `SCDynamicStore`（CFNetwork 层，无需写代码） |
| `curl` / `git` / `wget` | ✅ 读 | 环境变量 `http_proxy` / `https_proxy` / `all_proxy` |
| Go 的 `net/http` | ✅ 默认读 | 环境变量 `HTTP_PROXY` / `HTTPS_PROXY`（`httpproxy.FromEnvironment`） |
| `ollama` | ❌ **什么都不读** | — |
| 自己 `connect()` 的 socket 程序 | ❌ | — |

> 两类机制：**一部分框架替应用读系统设置**（CFNetwork 自动读 `SCDynamicStore`），**一部分工具只认环境变量**，**剩下的什么也不认**。
> 所以"代理生效"这件事，本质是**逐个程序分别生效**的，从来不是全局开关。

### 一条重要推论：代理协议通常只转发"连接"，不转发 DNS

客户端拿到域名后，**通常先在本地解析**，再把 IP 交给代理节点。于是：

- 代理能改变**连接走向**（我连谁）
- 但改不了**名字解析**（这个名字是谁）

这解释了一个真实故障：给 `ollama` 设了 `HTTPS_PROXY` 也没用——它**自己解析 DNS**，报错发生在解析结果的安全检查上，代理根本还没参与。

### fake-IP 机制

TUN 客户端为了**避免真 DNS 查询**、并在拿到连接时就知道"这是哪个域名"，对 DNS 请求返回一个**假 IP**：

```text
example.com ──DNS 请求──▶ TUN 客户端
                          │
                          ├─ 在内存里记下映射：example.com ↔ 198.18.0.39
                          └─ 返回假 IP：198.18.0.39

应用连 198.18.0.39
    ↓ 路由表把 198.18.0.0/15 指向 utun
TUN 客户端查表还原出域名 → 按规则分流（DIRECT / PROXY）
```

| 方面 | 说明 |
|---|---|
| 假 IP 段 | 常见 `198.18.0.0/15`（RFC 2544 保留的基准测试网段，不会和公网冲突） |
| 好处 | 省一次真 DNS 往返；连接建立时**立刻知道域名**，可按域名分流（不必只按 IP） |
| 副作用 | **别的程序看到的也是假 IP** |
| 退出后 | 映射消失，该 IP 不再可达 |

**真实故障**：`ollama pull` 报 `resolves to non-public 198.18.0.138`——ollama 做了 **SSRF 防护**（拒绝私有 / 保留地址），而 fake-IP 段正好命中。**这是安全检查在正常工作，不是 bug。**

### TUN 客户端为什么要自带用户态 TCP/IP 栈

内核把 IP 包交给 `utunN` 设备后，客户端拿到的是**裸 IP 包**——没有 socket、没有连接状态、没有序号管理。所以它必须**自己实现**：

- TCP 三次握手、序号与确认、重传、滑动窗口、拥塞控制
- UDP 会话映射
- （若要支持 ICMP）自己回 `echo reply`

> 所以"TUN 模式"重的**不是转发，是在用户态重造一个 TCP/IP 栈**。
> sing-box / mihomo 里的 `gvisor` 栈与 `system` 栈之争，本质就是"用户态栈"与"交给内核栈"的取舍。

### PAC（Proxy Auto-Config）

一个 JS 文件，导出 `FindProxyForURL(url, host)`，返回 `"DIRECT"` 或 `"PROXY host:port"`：

```javascript
function FindProxyForURL(url, host) {
  if (isPlainHostName(host) || shExpMatch(host, "*.cn")) return "DIRECT";
  return "PROXY 127.0.0.1:1082";
}
```

| | PAC | TUN + 规则 |
|---|---|---|
| 分流位置 | **应用层**（浏览器每次请求前调用） | **内核层**（按目标 IP / 域名） |
| 覆盖范围 | 只有读了 PAC 的应用 | 全部流量 |
| 现在还用吗 | 遗留方案，偶尔用于内网 | 主流 |

> PAC 是"规则分流"在**应用层**的早期形态；今天 `[Rule]` 段的 `GEOIP,CN,DIRECT` / `FINAL,PROXY` 是同一思想搬到了**内核层**。

### 常见误解

| 误解 | 真相 |
|---|---|
| 设了系统代理 = 全局代理 | 只是写了个配置项，**读不读由应用决定** |
| 走代理 = DNS 也走代理 | 代理协议通常只转发**连接**；DNS 多由客户端自行解析 |
| TUN 是"更高级的代理" | **不同层的东西**：TUN 换的是**路由**，代理换的是**终点** |
| fake-IP 是 DNS 被污染 | 是客户端**故意造假**用于分流，不是被劫持 |
| `HTTPS_PROXY` 能救所有网络故障 | 不读环境变量的程序（如 `ollama`）完全无效 |

### 验证与排查（可执行）

```bash
scutil --proxy                        # ① 系统代理到底设了什么
echo "$HTTPS_PROXY $HTTP_PROXY"       # ② 环境变量设了没
netstat -rn | head -3                 # ③ 默认路由指向谁：utunN = TUN 正在接管
dig +short example.com                # ④ 是否返回 198.18.x.x（fake-IP 生效中）

networksetup -setwebproxy Wi-Fi 127.0.0.1 1082      # 改系统代理
networksetup -setwebproxystate Wi-Fi off            # 关掉
```

判据速记：

- `netstat -rn` 默认路由是 `utunN` → **TUN 在强制接管**
- 默认路由是 `en0` 而 `scutil --proxy` 有值 → **只有系统代理，靠应用自觉**
- `dig` 返回 `198.18.x.x` → fake-IP 生效，**任何 IP 白名单/安全检查都可能误判**

## 一句话总结

普通代理更像“帮部分应用代发请求”，而 TUN/VPN 更像“改写整条网络路径”；`curl` 和 `ping` 是否都能通，核心取决于流量属于哪一层、是否被代理程序实际接管。

更根本的一条：**系统代理是自愿遵守的配置项，TUN 是内核强制的路由接管**——前者逐个程序分别生效，后者无人能拒。

## 相关问题

- 为什么浏览器能翻但终端某些命令不行？ → 因为浏览器常显式配置了代理，而终端工具未必跟着走同一套代理配置。
- SOCKS5 一定比 HTTP 代理高级吗？ → 不一定，只是更通用；是否更适合要看场景。
- 开了 TUN 还不通怎么办？ → 继续排查 DNS、路由、客户端实现、节点能力和系统权限。
- 系统代理和 TUN 的本质区别是什么？ → **自愿 vs 强制**：前者是应用主动去读的配置项，后者是内核按路由表转发、应用无法拒绝。
- 为什么设了代理 `ollama` 还是不走？ → 它**不读任何代理设置**，且自己解析 DNS；代理只管连接，管不了解析。
- 为什么开 TUN 后 `ollama pull` 报 "non-public 198.18.x.x"？ → TUN 的 **fake-IP** 触发了 ollama 的**内网地址安全检查**；关掉 TUN 即可。
- 为什么 TUN 客户端体积大、实现复杂？ → 它要在**用户态重造一个 TCP/IP 栈**（握手、重传、窗口、拥塞控制），因为内核给它的是裸 IP 包。

## 技术拓展

### 一个很实用的排查顺序

遇到代理问题时，可以按这个顺序排查：

1. 先确认代理节点本身可用
2. 再确认应用是否真的走了代理
3. 再看是 TCP、UDP 还是 ICMP 流量
4. 最后排查 DNS、路由和 TUN 权限

这样比一上来就改复杂配置更高效。

### 分层定位表（把症状映射到层次）

| 症状 | 大概率出在哪一层 |
|---|---|
| 浏览器能上、终端不通 | **系统代理**（终端没读设置 / 没设环境变量） |
| 全都上不去 | **路由**（默认路由 / TUN 未生效） |
| 域名解析异常、IP 是 `198.18.x.x` | **DNS + fake-IP** |
| 某个程序单独不通、报安全错误 | 该程序**自己解析 / 自己校验 IP** |
