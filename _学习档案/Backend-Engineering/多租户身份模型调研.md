# 多租户 B2B SaaS 身份模型调研

Decision status: accepted in FixFlow ADR 0010.

## 核心结论

1. FixFlow 应采用**全局用户身份 + 租户成员关系 + 成员关系上的角色**。
2. 同一个自然人只有一个 `app_user`，可在多个租户拥有不同的 `tenant_membership`；角色属于成员关系，不属于全局用户。
3. 每条成员关系默认支持多个角色。v1 可以只分配一个角色，但数据模型不应把“人永远只有一个职责”写死。
4. “每个租户一套重复账号”只在强身份隔离、独立目录或严格数据驻留要求下采用；FixFlow 当前没有这种约束。
5. 认证回答“我是谁”，租户成员关系回答“我在哪个租户里是谁”，授权回答“我在这个租户里能做什么”。

## 两种模型

| 维度 | A：全局身份 + 租户成员关系 | B：每个租户复制账号 |
|---|---|---|
| 身份粒度 | 一个自然人一个全局身份 | 每个租户各有一个账号 |
| 同一人多个租户 | 一个账号，多段成员关系 | 多套账号、密码和 MFA |
| 租户角色 | 角色绑定成员关系 | 角色绑定租户内账号 |
| 离职一个租户 | 停止该成员关系，不影响其他租户 | 删除或停用其中一个账号 |
| 邀请流程 | 邀请加入租户，可复用已有身份 | 每个租户重复邀请和开户 |
| 用户切换租户 | 选择租户后重新取得租户上下文 | 通常需要切换账号 |
| 审计 | 全局用户 ID 不变，租户成员关系区分上下文 | 同一自然人对应多个用户 ID，难以全局关联 |
| 隔离能力 | 依赖应用授权和查询始终带租户边界 | 身份目录天然分租户，隔离感更强 |
| 主要代价 | 必须正确维护身份与成员关系的边界 | 账号、凭据、MFA、通知和离入职管理重复 |

Microsoft 建议：在条件允许时为每个人建立一个身份，因为这会同时简化服务商和用户的账户管理，也便于身份平台执行威胁检测；只有个人/工作身份分离、强监管或数据驻留等场景才需要多个身份。[^ms-identity]

AWS 把“已认证用户 + 其所属租户”的绑定称为 SaaS identity，并要求租户上下文贯穿认证与授权链路，而不是等到业务代码里临时拼接。[^aws-identity]

Microsoft 的 B2B 租户模型把客户组织映射为 tenant，一个 tenant 通常包含多个用户；租户模型与部署形态是不同维度，不能因为共用一套部署就合并身份边界。[^microsoft-tenancy]

## 关键业务场景

### 同一人在两个租户拥有不同角色

```text
app_user: 张三
  ├─ membership(租户 A): DISPATCHER
  └─ membership(租户 B): TECHNICIAN
```

认证成功后只确定“张三”这个全局用户。用户选择租户 A 时，服务端加载租户 A 的有效成员关系和角色；切换到租户 B 时重新建立租户授权上下文。

Microsoft 明确描述了这种场景：同一用户可能在一个租户是管理员，在另一个租户只有有限权限，因此需要明确的租户切换机制，并防止租户上下文串用。[^ms-identity] Auth0 同样允许用户属于多个 Organization，并通过 `org_id` 标识当前组织。[^auth0-overview] [^auth0-token]

这意味着请求中的 `tenant_id` **不能单独作为授权依据**。服务端必须确认当前全局用户在该租户存在有效成员关系，再根据该成员关系的角色授权。

### 离开一个租户，但仍属于另一个租户

应停用或移除该用户的 `tenant_membership` 及其角色，而不是删除全局 `app_user`：

```text
张三的租户 A 成员关系：LEFT / INACTIVE
张三的租户 B 成员关系：ACTIVE
全局账号：仍可登录
```

Auth0 的成员移除语义也明确区分两者：从 Organization 移除成员只删除该组织中的 membership，不会删除用户或身份源记录。[^auth0-remove]

全局禁用与租户内停用必须分开：

- 全局账号禁用：该用户不能登录任何租户，适用于安全封禁。
- 租户成员关系停用：只撤销该租户内的访问，其他租户不受影响。
- 角色撤销或成员关系停用后，应让新请求立即按数据库最新状态拒绝；已有会话或令牌的生命周期策略另行设计。

### 邀请与账号生命周期

推荐流程：

1. 租户管理员向邮箱发出加入该租户的邀请。
2. 用户接受邀请并验证邮箱。
3. 若全局身份已存在，则关联已有 `app_user`；否则创建全局身份。
4. 创建或激活该租户的 `tenant_membership`。
5. 在成员关系下分配一个或多个角色。

“已邀请”不能等同于“已激活成员”。邀请未接受前不应获得业务权限。Auth0 的邀请流程也要求受邀者创建账号或登录，再加入 Organization；预分配角色只有在通过该 Organization 登录时才生效。[^auth0-invite]

当邮箱发生冲突时，不能仅凭字符串相同就自动合并且授予访问权。验证邮箱所有权后，本地认证可以建立全局用户；将来接入 OIDC/SAML 时，应进一步使用身份提供方的 `issuer + subject` 作为外部身份键。Microsoft 也建议授权和审计引用不可变的唯一标识，而不是可能变化的邮箱。[^ms-identity]

### 授权与租户隔离

推荐把认证与授权拆开：

```text
Authentication
  -> actorUserId（全局用户）
  -> 选择 tenantId
  -> 加载 ACTIVE tenant_membership
  -> 加载该成员关系的角色
  -> 领域授权
  -> 所有数据访问附带 tenant_id
```

AWS 要求租户上下文成为身份的一等属性，并贯穿各层；Auth0 还要求 API 验证组织标识，并按 `org_id` 隔离数据访问。[^aws-iam] [^auth0-token] 因此不能把 UUID、排序 ID 或“用户知道租户 URL”当作授权。

最低测试集合：

- 同一用户可在租户 A、B 获得不同角色。
- 用户在 A 的角色不能带入 B。
- 跨租户访问另一个租户的工单必须被拒绝。
- 成员关系停用后，该租户的新请求必须被拒绝。
- 停用 A 的成员关系不能影响 B。
- 同一 `(tenant_id, app_user_id)` 不能产生两条有效成员关系。

## 一个角色还是多个角色

| 方案 | 优点 | 缺点 | 适用条件 |
|---|---|---|---|
| 成员关系只有一个 `role_code` | 表少，权限计算简单 | 一人兼岗时要复制账号或改表；无法表达调度员兼技术员 | 业务保证岗位互斥且永不兼岗 |
| 成员关系有多个角色 | 符合兼岗和权限叠加；角色可独立授予、撤销和审计 | 多一张关联表，授权时取角色并集 | B2B 员工可能身兼多职 |

FixFlow 应选择**多角色模型**。维修公司的调度员可能需要临时处理工单，租户管理员也可能被明确授予调度职责。即使 v1 的种子用户暂时只有一个角色，多角色关联表也能避免以后用重复账号绕过限制。

Auth0 官方说明 Organization member 可以被分配一个或多个角色，且每个角色只在当前 Organization 登录上下文中生效。[^auth0-roles]

`TENANT_ADMIN` 仍不自动等于 `DISPATCHER`。多角色表达的是“可以显式叠加”，不是“管理员天然拥有所有业务权限”。

## 为什么角色属于成员关系

角色描述的是“这个人在这个租户里能做什么”，而不是“这个人在整个平台是什么”。

如果把 `role_code` 放在全局 `app_user`：

- 张三在租户 A 是调度员，会让他在租户 B 也获得调度员权限。
- 不同租户无法独立授予、撤销和审计角色。
- 离职一个租户会影响全局身份，或必须用更多字段区分租户，最终又回到成员关系模型。

Microsoft 将租户内角色描述为租户上下文的一部分，并建议在用户切换租户时取得带正确租户和角色的新令牌或授权上下文；Auth0 将 Organization role 限定在单个 Organization。[^ms-approaches] [^auth0-org-roles]

## FixFlow 推荐

### 模型

```text
tenant 1 ── N tenant_membership
app_user 1 ── N tenant_membership
tenant_membership 1 ── N tenant_membership_role
```

- `app_user`：全局身份、登录标识、显示名、全局启用状态。
- `tenant_membership`：用户属于哪个租户、成员状态和租户内生命周期。
- `tenant_membership_role`：成员关系下的一条角色授予；不要用逗号分隔字符串保存多个角色。
- v1 仍只开放一个种子租户，但关系模型允许同一用户以后加入其他租户。

### Java / Spring / MySQL 落点

| 约束 | 设计落点 |
|---|---|
| 身份与租户授权分离 | Spring Security 认证全局用户；应用服务加载 `TenantMembership` 后再做租户授权 |
| 角色属于成员关系 | `tenant_membership_role`，授权时按当前租户取角色并集 |
| 不信任客户端租户/角色 | 不读取请求体中的角色；`tenant_id` 必须对照当前用户的有效成员关系 |
| 唯一性 | 全局用户邮箱、`(tenant_id, app_user_id)`、`(tenant_membership_id, role_code)` 都需要数据库唯一索引 |
| ID | 延续项目 ADR 0003：内部关系用 `BIGINT UNSIGNED`，公开资源用 `CHAR(36)` UUID |
| 表结构 | 每张表保留 `id`、`create_time`、`update_time`；遵循项目固定的《阿里巴巴 Java 开发手册》基线。[^alibaba] |
| 引用完整性 | 手册约定不建数据库外键；创建成员关系和角色时由应用事务校验租户与用户存在 |
| 授权策略 | 角色只能做什么仍由领域代码决定，不在数据库 `CHECK` 中复制整套 RBAC 规则 |

Spring 侧可以从一个明确的 `CurrentActor(userId, tenantId, roles)` 上下文开始，但该上下文必须由服务端根据认证用户和有效成员关系构造，不能直接来自请求参数。

### 不采用租户复制账号的理由

Google Identity Platform 的 tenant 是包含独立用户、身份提供方、审计和 IAM 配置的隔离域，证明了“租户级身份目录”是正式模型。[^google-tenants] 但 FixFlow 需要解决的是普通维修服务公司之间的业务数据隔离，不是为每个客户提供独立身份目录。

如果未来某类租户要求独立 IdP、独立数据驻留或监管隔离，可以让该租户使用外部 IdP/独立认证域，同时仍把它的身份映射到 FixFlow 的全局用户和成员关系。不要因为“数据要隔离”就默认复制自然人账号；数据隔离和身份目录隔离是两个不同决策。

## 待后续确认

- v1 是否立即实现邀请流程，还是先由种子脚本创建用户与成员关系。
- 成员关系采用布尔启停，还是显式 `INVITED / ACTIVE / SUSPENDED / LEFT` 生命周期。
- 将来是否接入 OIDC/SAML；若接入，再增加外部身份表并采用 `issuer + subject`。

以上只确定身份模型方向，不代表应用代码或数据库迁移已经修改。
