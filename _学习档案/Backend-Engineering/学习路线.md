# Backend Engineering 学习路线

## 核心结论

1. 项目不是为了使用更多中间件，而是为了持续解决真实业务约束、并发冲突、一致性问题和故障恢复。
2. 首版采用多租户数据模型，但只启用一个种子租户；跨租户隔离从第一天进入约束和测试。
3. 首版不引入 Kafka、ES、Redis 或 RabbitMQ。第二版出现真实异步副作用后，使用 MySQL Outbox 和 Kafka。
4. 多租户、状态机、事务边界、时间与 ID 语义属于早期决策；搜索、消息、缓存和部署编排可以随需求演进。
5. 进度按完成证据计算：能解释、能实现、能制造故障、能定位、能恢复，并隔天仍能讲清。

## 产品定位

**FixFlow** 是面向设备维修服务公司的多公司工单协作平台。

首版业务边界：

- 一个部署支持多租户数据隔离。
- 首版只建立一个种子租户，不实现租户注册、套餐和计费。
- v1 的登录角色只有租户管理员、调度员和技术员。
- 客户和客户联系人是业务实体，不是登录主体；客户沟通由调度员代为记录。
- v1 状态为 Open、Assigned、In Progress、Resolved、Closed、Cancelled；不保留 Draft。
- 技术员可退回指派；只能操作分配给自己的工单。
- 租户管理员管理用户和配置，不默认拥有业务操作权。
- 核心流程是创建工单、分派、处理、解决和关闭。
- 首版暂不包含备件库存、在线支付、全文搜索和站外通知。

## 复杂度来源

复杂度必须来自业务，不来自组件数量：

- 多角色对同一工单执行不同命令。
- 多个用户并发修改同一工单。
- 状态转换和审计必须原子提交。
- 数据库提交后，通知和搜索等副作用可能失败。
- 同一事件可能重复、乱序或延迟到达。
- 搜索读模型可能与事实源短暂不一致。
- 跨租户访问必须默认拒绝。

## 不可逆与可后加

| 尽早决定 | 可以后加 |
|---|---|
| 租户边界与授权上下文 | Kafka |
| 工单状态机与业务不变量 | Elasticsearch |
| 金额、币种和时间语义 | Redis 缓存 |
| 数据库事务与幂等策略 | 消息重试平台 |
| 数据库迁移策略 | 部署编排方式 |
| 内部 ID 与公开 ID | 前端状态管理库 |

原则：跨所有表和接口、后期迁移成本高的决定早做；可替换的基础设施等业务触发后加入。

## 版本演进

| 版本 | 新增能力 | 明确不加入 |
|---|---|---|
| v1 | 租户隔离、登录授权、工单主流程、并发版本控制、审计、CI/CD、基础观测 | Kafka、ES、Redis、库存、支付 |
| v2 | MySQL Outbox、Kafka、Inbox、消费者重试、异步通知或读模型 | RabbitMQ、Kafka 与 RocketMQ 并用 |
| v3 | Elasticsearch 搜索投影、索引重建、版本冲突和降级 | 把 ES 当作事实源 |
| v4 | 备件库存、预留、消耗和库存流水 | 用应用内存代替数据库一致性 |
| v5 | 客户账单、在线支付、回调幂等、退款和对账 | 把支付状态直接塞进工单状态机 |
| v6 | 完整多租户运营：注册、邀请、配额、租户级观测 | 无边界地按租户复制整套基础设施 |

## 技术触发条件

### Kafka

至少在出现以下两类需求时加入：

- 工单状态提交后，通知、搜索、审计投影等多个消费者需要独立处理。
- 副作用不能阻塞 HTTP 请求，失败后必须重试或重放。
- 多个 worker 需要独立扩缩容。
- 需要消费 lag、重放和积压恢复能力。

加入顺序：

```text
业务事务
  -> 审计记录
  -> MySQL Outbox
  -> Kafka
  -> 多个消费者
```

Kafka 只保证 partition 内有序。消息键使用 `tenantId:ticketId`，消费者仍然需要 Inbox 去重和聚合版本校验。

### Elasticsearch

先在 MySQL 中实现搜索并建立目标数据量基线。只有出现以下情况才加入：

- 工单、评论和设备需要联合全文搜索。
- 需要分词、相关性、模糊匹配或复杂聚合。
- MySQL 查询在目标数据量下无法满足搜索 SLO。
- 业务能够接受搜索短暂落后于数据库。

推荐混合搜索：

```text
ES 召回并排序工单 ID
  -> MySQL 读取当前权威数据
  -> 应用恢复 ES 顺序
  -> 按 MySQL 当前租户和权限再次校验
```

### 备件库存

当维修会真实消耗共享备件时加入。必须实现：

- 可用量、预留量和库存流水。
- 条件更新或行锁防止超卖。
- 工单取消时释放预留。
- 并发压测和库存守恒测试。

### 在线支付

当外部客户必须付款，且付款状态决定工单是否继续时加入。支付需要独立状态机、回调幂等、退款和对账，不属于工单状态机内部。

## 状态一致性协议

每次业务命令遵循同一处理顺序：

1. 从会话获取租户和用户，不信任客户端传入的 `tenant_id`。
2. 校验角色、对象归属和当前状态。
3. 检查命令是否在当前状态的允许转换表中。
4. 使用 `aggregate_version` 做条件更新。
5. 更新行数不为 1 时返回并发冲突。
6. 同一数据库事务写入审计记录和 Outbox。
7. 提交事务。
8. 由 relay 发布 Kafka 事件。
9. 消费端使用 Inbox 去重并校验事件版本。

不要把 HTTP、短信、支付等远程调用放进数据库事务。

## 学习单元

每个学习单元按以下顺序执行：

1. 定义要解决的业务问题。
2. 写出正常流程、失败流程和业务不变量。
3. 比较至少两个方案及其触发条件。
4. 先说明设计，再写代码。
5. 运行测试，并主动制造重复、并发、超时或宕机。
6. 查看日志、指标和数据结果。
7. 独立复述机制，找出前置概念缺口。
8. 写入领域笔记、学习日志和 ADR。

## 阶段完成证据

| 阶段 | 完成证据 |
|---|---|
| 业务建模 | 能说清角色、命令、状态、不变量和非目标 |
| 首版纵切 | 登录、创建、列表、详情形成真实链路 |
| 状态与并发 | 并发冲突、非法转换和审计原子性测试通过 |
| 异步一致性 | 数据库提交后崩溃不丢事件，重复消费不重复生效 |
| 搜索 | ES 不可用和索引延迟时仍有明确降级行为 |
| 库存 | 并发预留不超卖，流水与余额可对账 |
| 支付 | 重复回调、延迟回调和退款均有隔离测试 |
| 多租户 | 跨租户访问全部被拒绝，索引、缓存和日志均带租户边界 |
