## 第一段 · 注意力执行细节（2026-10-01）

**学了**：注意力三步（`QKᵀ` 打分 → softmax 归一化 → 加权求和 V）→ 输出 o → `h = h + o`；大写 `W`（参数）与小写 `w`（注意力权重）的区别；Q/K/V 的角色分工

**产出**：[[大模型推理基础]] 补「矩阵形状约束」「o 的去向」；[[KV-Cache原理]] 补「行 × 宽度两个旋钮」

**我犯过的错**

| # | 我当时的想法 | 错在哪 |
|---|---|---|
| 1 | 历史 token 的 **Q** 也参与计算 | 历史只留 **K/V**；Q 是当前 token 现算、**用完即弃** |
| 2 | "`W_Q` 是给 Q 加权的系数" | `W_Q` 是**投影矩阵**，作用在 **h** 上、用来**造出** Q |
| 3 | 把注意力权重 `w` 与模型权重 `W` 混为一谈 | 大写 `W` 是训练得到的参数（**冻结**）；小写 `w` 是每步 `softmax(QKᵀ)` **现算**的 |
| 4 | "o 是**注意力参数**" | o 是**注意力输出 / 上下文向量**，是数据不是参数 |
| 5 | "o 是对 h 的**微调**" | o 是推理阶段的**改写量 Δ**；微调（fine-tuning）是**训练阶段改 W** |

**顺带记住**：中文"权重"一词同时对应 `weights`（参数）和 `attention weights`（注意力权重），**说的时候必须区分**。

## 第二段 · 多头切分与 GQA（2026-10-01 深夜 ~ 10-02）

**学了**：多头切的是**输出维度**（W 按列切），h 完整输入；投影矩阵「行数必须匹配、列数自由」；点积 vs 矩阵乘（`Q·K` = `Q × Kᵀ`）；MHA / GQA / MQA 是按"每组几个 Q 共享一份 KV"构成的**连续谱**；GQA 省显存的机制

**产出**：[[大模型推理基础]] 补多头切分与 `QKᵀ` 形状；[[KV-Cache原理]] 补三种方案的正式名称与"少了两份"的真正含义

**我犯过的错**

| # | 我当时的想法 | 错在哪 |
|---|---|---|
| 6 | "h 是 4096 维，所以 **Q 和 K 也必须是 4096 维**" | 只有**行数**受 h 约束；**列数（输出维度）是设计自由度** |
| 7 | "K 只有 8 段，那不就**差位数**了吗" | Q 段数与 KV 段数**不必相等**；必须相等的是**每段宽度**；Q 段数须是 KV 段数的**整数倍** |
| 8 | "**KV 的宽度**不是 token 数量决定的吗" | token 数决定**行数**（长度）；**宽度 = KV 头数 × 每头维度** |
| 9 | "**下投影**和 K 运算得到 c" | 方向反了：**h → c → K**；压缩必须发生在 K 诞生之前 |
| 10 | "吸收只是**换了个计算顺序**，快在哪" | **质疑成立**，是我没讲清 t：`W_UK` 作用 **1 次**（作用于 Q）vs **t 次**（作用于每个历史 c） |

**值得记住的一次胜出**：第 10 条是**我质疑对方讲得不清楚，最后证明我是对的**——它把"weight absorption 省在哪"逼到了 t 这个维度上。**质疑讲不清的地方，比自己硬啃有效。**

## 第三段 · MLA 与 RoPE（2026-10-02 晚 ~ 10-03）

**学了**：MLA 低秩压缩（`h →下投影→ c →上投影→ K/V`，缓存只存 c；2026-10-07 更正：还应加上位置段 `k_rope`）；weight absorption（`W_UKᵀ` 合并进 Q，`W_UV` 重排至加权之后）；算术强度视角（吸收把 decode 从 compute-bound 拉回 memory-bound）；RoPE 机制（旋转、相对位置、多频率）；MLA × RoPE 冲突与 **decoupled RoPE**

**产出**：新建 [[MLA原理与RoPE解耦]]（158 行）；[[大模型推理基础]] 的 RoPE 段从 1 行扩为 6 条要点

**我犯过的错**

| # | 我当时的想法 | 错在哪 |
|---|---|---|
| 11 | "上投影 × 下投影**化为归一、相当于没有作用**" | 是**合并成一张低秩矩阵**（结合律），**不是抵消成单位矩阵**（逆运算）。4096→512 有信息损失，不可能无损还原 |
| 12 | 把 RoPE 记成 **ROUGE** | ROUGE 是文本摘要评测指标，与位置编码无关。**RoPE = Rotary Position Embedding** |
| 13 | 以为"只给相对位置"会导致模型无法定位 | ✅ 反过来才对：语言理解**只需要相对关系**；"猫追狗"在开头还是中间，含义相同 |

**同时被纠正的（对方也错了）**

| 说错的话 | 纠正 |
|---|---|
| "吸收失效是因为**旋转是非线性的**" | ❌ 旋转**是线性的**。真正原因是 `R_n` **逐 token 不同**，无法预先合并成固定矩阵 |

> **这一栏的意义**：老师也会说错。**带着验证的心态听，比全盘接受更安全。**

**产出**：`_学习档案/LLM-Foundations/kv_calc.py`（参数化估算工具）

**我犯过的错**

| # | 我当时的想法 | 错在哪 |
|---|---|---|
| 14 | 不知道 **fp16** 是什么 | fp16 = 16 位 = **2 字节**；它就是你算显存时"每个数占几字节"那一项 |
| 15 | 式子写成 `32×8×2×128×1000` | 少一个 `×2`（fp16 每数 2 字节）+ token 数少一个 0 → **结果差 20 倍**（62.5 MiB vs 1.22 GiB） |

**被纠正的（我也错了）**

| 说错的话 | 纠正 |

**实测对照**（同一个模型，只改 KV 头数）

| 配置 | KV 头 | 宽度 | KV Cache |
|---|---:|---:|---:|
| GQA（现代默认） | 8 | 1024 | **1.22 GiB** |
| MHA（老配置） | 32 | 4096 | 4.88 GiB |

**方法论（这次做对了的）**：怀疑一个成因时，别靠回忆——**先写检测器把现象量化，再找对照组**。

| 步骤 | 做法 | 结果 |
|---|---|---|
| 量化 | 扫 `session.v4.jsonl.zstd`，统计推演块里**同一行最大连续重复数**（`maxrun`） | 正常轮 `maxrun ≤ 2`；病态轮 `79–1153`——**二值可分** |
| 定位 | 逐轮对齐 maxrun / 时长 / 输出字数 / 结束原因 | 断崖：轮 105 `maxrun=2` → 轮 106 `maxrun=1153` |

| 验证 | 手动 `/compact`（312 项 / ~147K tokens）后观察 | 轮 126、127 `maxrun=1`，**恢复** |

**实验 B 数据**（qwen3.5:9b / Q4_K_M / `think=false` / temperature 0）

| 实际输入 token | TTFT | prefill | TPOT |
|---|---:|---:|---:|
| 3057 | 26.53 s | 20.21 s | 62.0 ms |
| 4098 | 27.75 s | 27.61 s | 64.8 ms |

- **prefill 随输入线性增长** ✅（输入 +34% → prefill +37%）→ 验证 compute-bound
- **TPOT 基本稳定** ✅（+4.5%）→ 验证 memory-bound
- ⚠️ **异常**：3K token 的 prefill 竟要 20 秒 → 查到 **swap 用了 5.2 GB**

**排障三关（真实的工程经验）**

| # | 症状 | 根因 | 解法 |
|---|---|---|---|
| 1 | `ollama pull` 报 **HTTP 412** | 客户端 0.13.2 < 模型元数据要求的 **0.17.1** | `brew upgrade ollama` → 0.35.1 |
| 2 | 下载报 *resolves to non-public 198.18.0.39* | **fake-IP**（TUN 的 DNS 劫持）被 ollama 的安全检查拒 | **关 TUN**（走代理无效——它自己解析 DNS，代理只管连接） |
| 3 | 推理慢到 20 秒 | **内存容量不足 → swap**（15G used / 118M unused） | 降上下文 / KV 量化 / 关应用 / 换小模型 |

> **容量 vs 带宽**：带宽不够是**变慢**，容量不够是**塌方**——今天亲眼看到了后者。

**产出**：新建 [[MoE与DeepSeek成本结构]]、[[DSA稀疏注意力]]；更新 [[复习清单]]、[[学习路线]]、[[知识地图.canvas]]、README 索引；[[MLA原理与RoPE解耦]] 与成本调研补双链。

**我犯过的错**

| # | 我当时的想法 | 错在哪 |
|---|---|---|
| 27 | 把 MLA 当成 DeepSeek “又便宜又好”的根本原因 | MLA 只解释 KV 存储和长上下文成本。它不解释模型能力。缺的前置概念是 **MoE**：总参数提供容量，激活参数控制每 token 计算量 |
| 28 | 把 KV Cache 说成“只存 c” | 漏了 **`k_rope`**。decoupled RoPE 下缓存 = `c + k_rope`；位置段小，但必须存 |
| 29 | 把 MoE 的“省计算”理解成“省显存” | MoE 省的是每 token FFN 计算量。**所有专家权重仍然要存在显存里** |
| 30 | 以为 Router 要运行每个专家才能打分 | Router 只做一次矩阵乘法：`g = h × W_g`。它比较的是 hidden state 和专家的**偏好向量**，不运行专家 FFN |
| 31 | 把 Attention 稀疏化说成“稀释” | 方向反了。“稀释”是权重分散到很多 token；“稀疏化”是只保留少数连接。DSA 让注意力更集中 |
| 32 | 以为 DSA 不用给低相关 key 打分 | DSA 的 **indexer 仍要给所有历史 key 打便宜分数**，再选 top-k。省的是后续昂贵的 QK，不是全部相关性判断 |

**方法论**：区分两类稀疏。MoE 稀疏的是 token ↔ 专家 FFN；DSA 稀疏的是 token ↔ token 注意力。两者都遵循同一个成本原则：把“能力”和“成本”拆开。

**被纠正的（我也错了）**

| 说错的话 | 纠正 |
|---|---|
| 先用 `logits`、`LM head` 和 `W_out` 解释 Temperature，却没有先定义它们和输出形状 | 生成链路必须先给完整形状流：`h_L → W_out → logits → softmax → token ID`，再讲 Temperature |

## 2026-10-24 · Backend-Engineering · UUID 存储与工程规约

**学了**：UUID 是固定的 128 位值，规范文本固定 36 字符；数据库内部主键和公开标识承担不同职责；《阿里巴巴 Java 开发手册（黄山版）》对定长字符串要求使用 `CHAR`；手册的【强制】、【推荐】、【参考】需要转化成不同的执行门槛。

**产出**：新建 [[UUID存储与MySQL字段设计]]；FixFlow 新增工程基线 ADR 与项目级 `AGENTS.md`；更新公开 ID ADR、Backend Engineering 学习路线和复习清单。

**这轮完善了什么**

| # | 之前的想法 | 更准确的理解 |
|---|---|---|
| 1 | 公司生产表常见 `VARCHAR`，所以它可能是默认最优方案 | 常见主要来自可读性和工具兼容；定长 UUID 文本应按手册使用 `CHAR(36)` |
| 2 | 128 位 UUID 和 64 位 `BIGINT` 看起来互相冲突 | 两者职责不同：`BIGINT` 管内部关系，UUID 管对外标识 |
| 3 | “遵循开发手册”可以在编码结束后再检查 | 手册应在业务与存储设计阶段作为前置门槛 |

**被纠正的（我也错了）**

| 说错的话 | 纠正 |
|---|---|
| 上一轮优先推荐 `VARCHAR(36)` 或 `BINARY(16)` | 固定文本长度应使用 `CHAR(36)`；二进制表示是后续有测量依据时再考虑的优化 |
| 只按磁盘字节数比较 UUID 类型 | 还要比较开发可读性、工具兼容性、索引和运维转换成本 |

**方法论**：先固定规范版本，再把规则等级映射为执行门槛。设计决策必须同时说明业务约束、规约依据、原因、方案和代价。

**本轮复述**：UUID 文本长度固定，所以使用 `CHAR(36)` 而不是 `VARCHAR(36)`。机制判定通过；术语上需要区分“UUID 值”和“UUID 的规范文本表示”。

**恢复点**：公开 ID 存储已经明确。下一步先确认工单是否保存联系人快照，再设计 v1 聚合边界和最小表集合。

**学了**：数据库负责保护数据形状和稳定不变量；领域代码负责授权、状态转换和需要上下文的业务规则。业务唯一字段必须由数据库唯一索引兜底，但“某个角色能否开始工单”属于领域策略，不应写进表约束。

**这轮完善了什么**

| # | 之前的理解 | 更准确的理解 |
|---|---|---|
| 1 | 事件表增加了很多 `CHECK`，看起来更严谨 | 约束数量不是目标；重复状态机和事件语义会增加漂移成本 |
| 2 | API、领域、数据库都校验像重复劳动 | 三层处理不同故障场景，简单边界校验可以重复，复杂业务规则只保留一个权威来源 |
| 3 | 新增角色权限变化可能意味着改数据库 | 授权策略属于领域代码；角色策略变化不应自动演变成表结构迁移 |

**被纠正的（我也错了）**

| 说错的话 | 纠正 |
|---|---|
| 在事件表加入 `chk_work_order_event_origin` | 事件构造规则交给领域代码与测试；数据库只保留结构合法性 |

**本轮复述**：只有当前技术员能开始工单，属于领域授权；以后增加新角色只需调整领域策略，不应修改数据库约束。机制判定正确。

## 2026-10-24 · Backend-Engineering · 多租户身份模型

**学了**：认证回答“这个人是谁”，租户成员关系回答“这个人在当前租户里是谁”，授权回答“他在这个租户里能做什么”。同一个自然人应有一个全局 User，但可以在多个 Tenant 中各有一段 Membership；角色属于 Membership，不属于全局 User。

**被纠正的（我也错了）**

| 之前的设计 | 为什么不完整 |
|---|---|
| User 属于且仅属于一个 Tenant | 同一个员工可能服务多个租户，并在每个租户拥有不同角色 |
| 角色直接挂在 User 上 | 角色是租户上下文的一部分，放在全局用户上会串租户 |
| 工单创建人、负责人、执行人直接引用 User ID | 工单属于某个租户，人员身份应引用该租户下的 Membership |

**方法论**：先判断同一自然人是否可能跨租户工作。如果是，就把全局身份和租户内员工关系拆开；如果要求身份目录完全隔离，则属于独立 IdP 或数据驻留问题，不应默认用复制账号解决。

**设计确认**：采用全局 User + Tenant Membership + 成员关系多角色；v1 可以只启用一个种子租户，但模型保留跨租户成员关系。

**关键约束**

- `tenant.slug` 全局唯一
- `(tenant.id, branch.slug)` 在租户内唯一
- `app_user.email` 全局唯一
- `(tenant_membership.tenant_id, app_user_id)` 唯一
- `(tenant_membership_role.tenant_membership_id, role_code)` 唯一
- 邀请不是 Membership；未接受邀请不应获得员工权限

**恢复点**：身份五表设计已经稳定，尚未修改 Flyway。下一步设计 Customer、Customer Contact 和 Equipment，再统一进入迁移与数据库测试。

## 2026-10-31 · Backend-Engineering · Go 方法接收者与接口

**学了**：Go 方法是带显式接收者的函数。类型定义方法集，实例提供字段值。接口由方法集隐式满足，编译器比较方法名、入参和出参，不比较函数体。小服务在 `main` 中从底层依赖向上显式装配。

**产出**：新建 [[Go方法接收者与接口]]；补齐 receiver、隐式接口、构造器、组合根和同名方法的多层关系。

**本轮复述**

> 函数名，入参、出参。签名

判定通过。正确抓住接口匹配的核心是方法签名。

**我犯过的错**

| # | 我当时的想法 | 错在哪 |
|---|---|---|
| 1 | `service` 变量好像前面从未出现 | 它由 `main` 中的 `service := NewService(...)` 创建，随后存入 Handler |
| 2 | `s *Service` 的接收者类型就是 `Service` | 基础类型是 `Service`，但接收者变量 `s` 的实际类型是 `*Service` |
| 3 | `type Store interface { List }` 就能表达接口 | 必须写完整方法签名：方法名、入参和返回值 |
| 4 | 接口可能和函数实现有额外隐式连接 | Go 只按方法集与签名做结构化匹配，函数体不参与 |
| 5 | Service.List 和 MySQLStore.List 可能是同一个方法 | 它们同名但接收者类型不同，是两个不同方法 |

**恢复点**：已能复述接口匹配规则。下一篇继续理解构造器和组合根，随后再进入 `POST /api/v1/work-orders` 的事务路径。
