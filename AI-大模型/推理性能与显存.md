# 推理性能与显存

为什么 decode 慢、为什么批处理几乎免费，以及服务端那个"中间层"长什么样。

## 问题

为什么生成一个 token 要等那么久？为什么批处理能把吞吐提高十几倍？显存带宽和显存容量分别在限制什么？

## 回答

### 核心结论

1. **Prefill 是 compute-bound，Decode 是 memory-bound**——慢在搬数据，不在算数。
2. Decode 每生成一个 token 都要把权重和整本 KV 账本从显存搬一遍。
3. **批处理把"搬一次权重"摊给多个请求**，这是 memory-bound 世界的免费性能。
4. batch 里的"多"是**多个不同请求**，不是同一请求的多个 token。
5. 显存**容量**决定并发数，显存**带宽**决定生成速度——两个独立瓶颈。

### 1. compute-bound vs memory-bound

| 中文 | English | 定义 |
|---|---|---|
| **访存受限** | **memory-bound** | 瓶颈在数据搬运速度 |
| **计算受限** | **compute-bound** | 瓶颈在计算能力 |
| **显存带宽** | **memory bandwidth** | 每秒能从显存搬多少字节 |
| **算术强度** | **arithmetic intensity** | 每搬 1 字节能做多少次浮点运算 |

**注意区分容量与带宽（两个独立瓶颈）：**

| | 决定什么 | 优化手段 |
|---|---|---|
| 显存**容量** capacity | 能同时服务几个请求 | GQA / MLA / 量化 / KV 驱逐 |
| 显存**带宽** bandwidth | 生成速度（tokens/s） | 批处理 |

**算一笔账**（高端卡量级：带宽约 3 TB/s，算力约 1000 TFLOPS fp16）：

```text
decode 一个 token 要搬：权重 ~14 GB + KV ~6 GB = ~20 GB
                     要算：~14 GFLOPs

搬 20 GB：     20 ÷ 3000 GB/s ≈ 6 毫秒
算 14 GFLOPs： 14 ÷ 1000     ≈ 0.014 毫秒
                             ─────────
                     搬数据比算数慢 400 多倍
```

**每个 token 的 6 毫秒里，5.99 毫秒在等数据。** 这就是 memory-bound 的实感：**算力几乎全程闲着。**

### 2. 批处理

**本质**：模型权重只有一份，让"搬一次权重"服务更多 token。

| 配置（4K 上下文） | 要搬 | 产出 | 摊到每 token |
|---|---|---:|---:|
| batch = 1 | 14 GB 权重 + 0.5 GB KV | 1 个 | **14.5 GB** |
| batch = 32 | 14 GB 权重 + 16 GB KV | 32 个 | **0.95 GB** |

**吞吐提升十几倍，而单请求延迟几乎不变**——因为在 memory-bound 世界里，权重读取这个固定成本被摊薄了。

**必须搞清的一点**：

| | 能否批 | 原因 |
|---|---|---|
| 同一请求的多个 token | ❌ | token 之间有前后依赖（自回归） |
| **不同请求之间** | ✅ | 互不依赖，且共用同一份权重 |

### 3. 服务端架构

```text
  用户 A ─┐
  用户 B ─┼──▶ API 网关 ──▶ 调度器 ──▶ 模型实例（权重常驻显存）
  用户 C ─┘   gateway     scheduler      │
                                         ├── KV 管理器：A/B/C 各自账本
                                         ▼
                                一次算完，按请求拆开返回
```

| 中文 | English | 角色 |
|---|---|---|
| API 网关 | gateway | 接收请求、鉴权、限流 |
| 调度器 | scheduler | 决定这一步哪些请求组成 batch |
| 模型实例 / 副本 | model instance / replica | 跑在 GPU 上；每个副本各存一份权重 |
| 并发数 | concurrency | 能同时服务几个（被显存容量卡死） |

### 4. "搬"要分三个层次，不能混

| 层次 | 搬什么 | 频率 | 术语 |
|---|---|---|---|
| ① 磁盘 → 显存 | 模型权重 | **一次** | model loading |
| ② 显存 → 计算单元 | 权重 | **每一步** | weight read |
| ③ 显存 → 计算单元 | 各请求 KV | **每一步** | KV cache read |

**②③ 是瓶颈，发生在 HBM（显存）与 SM（流式多处理器）之间**，不是在网络上搬。

| 角色 | 谁 |
|---|---|
| 存放全部数据 | **HBM**（高带宽显存） |
| 真正做运算 | SM 里的运算单元 |
| 临时放"正在算的那一小块" | **SRAM / 寄存器**（片上是几百 KB 级） |
| 决定搬什么 | 编译器 + kernel 指令 |
| 实际搬运 | 显存控制器（硬件自动） |

**关键：不是"把权重交给 SM"，而是"流过去"。**

> 显存 80 GB vs 片上存储几十 MB，差约 1000 倍以上——**装不下**。数据是**分块（tiling）流经** SM 的：取一块 → 算 → 丢掉 → 取下一块。

**为什么必须隔开**：batch 内不同请求**绝不能串扰（cross-contamination）**。工程上不只是加 mask——各请求序列长度不同，padding 会浪费算力，所以用 **varlen attention / sequence packing**（`cu_seqlens` 标出每段边界）或 **block table**。

### 5. 进阶机制

| 中文 | English | 作用 |
|---|---|---|
| **连续批处理** | **continuous batching** | 每步重组 batch，谁做完谁走，新请求随时进来 |
| **分块预填充** | **chunked prefill** | 长 prefill 切块，与 decode 混跑，避免阻塞同批 decode |
| **预填充-解码分离** | **PD disaggregation** | prefill 与 decode 分别部署，各跑最优配置 |
| 流水线并行 | pipeline parallelism | 32 层切到多张卡，用微批次填满流水线 |

## 常见误解

| 误解 | 纠正 |
|---|---|
| "搬权重是从磁盘搬到显存" | 那是**模型加载**（一次）；每步的搬运是 **HBM → SM** |
| "把权重交给 SM" | SM 装不下，数据是**流过去**的 |
| "batch 是把同一请求的多个 token 一起算" | 是**多个不同请求**各算 1 个 token |
| "瓶颈在算力" | decode 的瓶颈在**显存带宽**，算力几乎全程闲着 |
| "KV Cache 占的是显存带宽" | 应分开说：**占容量（决定并发），吃带宽（决定速度）** |
| "批处理会增加很多延迟" | memory-bound 下权重读取被摊薄，延迟几乎不变 |

## 相关问题

- **为什么长上下文会让生成变慢？** → decode 每一步都要把整本 KV 账本读一遍；上下文越长，账本越厚，每步搬得越多。
- **为什么 MQA/GQA/MLA 能提速又提并发？** → 它们减小了 K/V 体积：**容量**上能塞下更多请求，**带宽**上每步搬得更少。
- **单张卡能服务多少人？** → 由显存容量决定。80 GB 卡跑 7B 模型，留给 KV 约 60 GB：5 万 token 上下文约 9 个并发，1 万 token 约 45 个。
