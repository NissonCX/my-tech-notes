# API 网关的鉴权与传输安全

API 网关最先执行的两段代码：**你是谁**（鉴权）、**你还能用多少**（配额）；以及它们赖以成立的底座——**HTTPS**。

## 问题

MaaS 平台的 API 网关怎么做鉴权？API Key / JWT / HMAC 各自怎么实现、怎么选？配额要限哪些维度？为什么"只限 QPS"不够？没有 HTTPS 时签名能保证安全吗？

## 回答

### 核心结论

1. 鉴权回答"你是谁"，配额回答"你还能用多少"；**两者都必须在前置网关完成**，不能等服务端返回。
2. **JWT 保证完整性，不保证机密性**——payload 谁都能解开，所以里面**不能放密钥**。
3. **API Key / JWT / HMAC 的安全性，根本前提是 HTTPS**；没有 TLS，签名只能防篡改，防不了窃听。

### 1. 鉴权三件套

| 方式 | 怎么工作 | HTTP 形态 | 取舍 |
|---|---|---|---|
| **API Key** | 固定字符串，查存储得到租户 | `Authorization: Bearer sk-xxx` | 简单；**每次要查库**（需缓存） |
| **JWT** | 自包含签名令牌 | `Authorization: Bearer eyJ...` | **不查库**；但**签发后难撤销** |
| **HMAC 签名** | 对请求内容签名 | `X-Api-Key` + `X-Timestamp` + `X-Nonce` + `X-Signature` | **防篡改 + 防重放**；客户端复杂 |

**JWT 的三段结构**：

```text
header.payload.signature

header   : {"alg":"HS256","typ":"JWT"}
payload  : {"sub":"tenant-123","iss":"maas","exp":1730000000,"scope":["chat"]}
signature: HMAC-SHA256(header + "." + payload, 服务端密钥)
```

验证方式：**用密钥重算签名**，比对一致即未被篡改。

**HMAC 签名的构造**：

```text
payload_hash = SHA256(请求体)
signature    = HMAC-SHA256(secret, method + path + timestamp + nonce + payload_hash)
```

其中 `timestamp` + `nonce` 用于**防重放**。

### 2. JWT：完整性 ≠ 机密性

```text
✅ 保证完整性：改了 payload，签名对不上 → 篡改被发现
❌ 不保证机密性：payload 只是 Base64，谁都能解开 → 不能放秘密
```

**所以 payload 里放的是 claims（声明），不是凭证**：

```json
{ "sub": "tenant-123", "exp": 1730000000, "scope": ["chat", "embedding"] }
```

**JWT 的取舍**：

```text
好处：无状态、不查库 → 网关可水平扩展
代价：签发后无法撤销 → 封禁用户在过期前仍有效
解法：短有效期（15 分钟）+ refresh token，或维护已吊销 jti 的黑名单
```

### 3. API Key 的完整工程流程

```text
① 签发：生成随机串 → 【只存哈希】入库 → 明文只显示一次
② 传输：Authorization: Bearer sk-xxx（走 HTTPS）
③ 校验：算哈希 → 查 Redis 缓存 → 未命中再查库并回填（TTL 5 分钟）
④ 注入：把 tenant_id / tier / scope 塞进请求上下文
⑤ 失败：401，并且【失败也要限流】（防暴力枚举 Key）
```

**三个容易漏的点**：

```text
· 只存哈希         ← 数据库泄露也拿不到原始 Key
· 加缓存           ← 否则每请求打一次库，网关自己先崩
· 失败也限流       ← 否则攻击者可每秒试几万个 Key
```

### 4. 配额：两个不同的桶

| | **速率限制** rate limit | **配额** quota |
|---|---|---|
| 管什么 | 单位时间内的**速率** | **累计总量** |
| 例子 | QPS、**TPM**、并发数 | 每月 100 万 token / 每月 50 元 |
| 超了怎么办 | 拒绝或排队，**下周期自动恢复** | 拒绝，**等下月或充值** |

**速率限制的三个维度（缺一不可）**：

| 维度 | 单位 | 讯飞实际值 |
|---|---|---|
| QPS / RPM | 每秒 / 每分钟请求数 | 秒级流控（错误码 `11202`） |
| **TPM** | **Tokens Per Minute**（每分钟 token 数） | 200w / 300w / 500w 三档 |
| 并发数 | 同时在跑的请求数 | 统一 20 路（错误码 `11203`） |

```text
只限 QPS → 一个请求带 10 万 token 就压垮后端
只限 TPM → 1000 个 1-token 小请求瞬间打满连接
只限并发 → 慢请求长期占坑，新请求永远排队
```

### 5. 四种限流算法

| 算法 | 特点 |
|---|---|
| 固定窗口 | 最简单；窗口边界有突刺（跨窗口可过 2 倍） |
| 滑动窗口 | 平滑；要存每个请求时间戳，成本高 |
| 漏桶 | 匀速放行，**不允许突发** |
| **令牌桶** ⭐ | 允许突发，最常用 |

```text
令牌桶：
  桶容量 = 突发上限
  每隔 1/rate 秒放入 1 个令牌
  请求消耗令牌；桶空则拒绝或排队
```

**三个工程坑**：

| # | 坑 | 后果 |
|---|---|---|
| 1 | 配额没在网关层算 | 后端返回时钱已经花了 |
| 2 | 流式请求只在入口检查一次 | token 边收边涨，配额会被突破 |
| 3 | 多实例各自计数 | 3 个实例 = 实际配额变 3 倍，需 Redis 集中计数 |

### 6. TLS：三层保护

| 目标 | 靠什么 |
|---|---|
| **机密性** | 加密 |
| **完整性** | MAC / AEAD |
| **身份认证** | 证书 + CA 信任链 |
| **前向保密** | ECDHE |

**混合加密（hybrid cryptosystem）**：

```text
握手（一次性，慢无所谓）：用非对称密码学【协商】出会话密钥
传输（全程）            ：用对称加密 + 会话密钥跑数据
```

**握手简化流程（TLS 1.3）**：

```text
客户端 ──ClientHello（支持的算法 + ECDHE 参数）──▶
服务器 ──ServerHello + 证书 + ECDHE 参数────────▶
双方各自算出同一个会话密钥（密钥从未在网络上传输）
之后全部用会话密钥对称加密
```

**证书链**：

```text
系统内置根 CA → 中间 CA → 服务器证书（含公钥）
客户端逐级验签，最终信任操作系统内置的根证书
```

**关键澄清**：TLS 里**没有"用非对称加密来加密数据"这一步**。非对称密码学只干两件事：

```text
① 验证签名（证书链）—— 确认身份
② 协商密钥（ECDHE）  —— 产出会话密钥
```

### 7. 对称加密为什么快

| | 对称（AES） | 非对称（RSA） |
|---|---|---|
| 核心运算 | 异或、查表、移位 | **大数模幂** `m^e mod n` |
| 操作对象 | 8~128 位 | **2048 位大整数** |
| 一次加密代价 | 几十个时钟周期 | **几百万个时钟周期** |
| 硬件支持 | **AES-NI 指令** | 无 |

**差 1000~10000 倍**——不是实现问题，是**数学运算本身的成本差异**。

**最简形态：异或**

```text
明文 1011 0110 ⊕ 密钥 1100 1010 = 密文 0111 1100
密文 0111 1100 ⊕ 密钥 1100 1010 = 明文 1011 0110    ← 加解密同一个操作
```

**但纯异或不可用**：`c1 ⊕ c2 = m1 ⊕ m2`，密钥被消掉，攻击者能推出明文关系。

**AES 的做法**：把主密钥扩展成多把**轮密钥**，分 10~14 轮混入：

| 步骤 | 作用 |
|---|---|
| SubBytes（S-box 替换） | **混淆** |
| ShiftRows（行移位） | **扩散** |
| MixColumns（列混合） | **扩散** |
| **AddRoundKey（⊕ 轮密钥）** | **这里是真正用到密钥的地方** |

**安全性来自"混淆 + 扩散 + 足够轮数"**，不是来自"运算复杂"。

### 8. 前向保密：RSA vs ECDHE

| | **RSA 密钥交换**（TLS 1.2 及以前） | **ECDHE**（TLS 1.3 强制） |
|---|---|---|
| 怎么协商 | 客户端用服务端**公钥加密**随机数发过去 | 双方各出一半参数，**各算各的** |
| 该随机数上过网？ | ✅ 上过（密文） | ❌ **从未上过网** |
| 前向保密 | ❌ 私钥泄露 → 解历史流量 | ✅ 私钥泄露也解不开历史会话 |

**为什么必须 HTTPS**：签名防篡改、防重放，但**请求内容、签名本身都在网络上明文**——没有 TLS，一切被看光，签名还能被原样重放。

## 常见误解

| 误解 | 纠正 |
|---|---|
| "JWT 的 payload 里可以放 API Key" | payload 是 **Base64 明文**；JWT 保完整性不保机密性 |
| "没有 HTTPS，用签名也能安全" | 签名防篡改/重放，**防不了窃听**；请求内容与签名本身都明文 |
| "非对称加密用来加密数据" | TLS 里它只做**验签**和**协商密钥**；数据全程由对称加密 |
| "对称加密不安全，所以才用非对称" | 对称**又快又安全**；用非对称只是因为**密钥分发**问题 |
| "限流只要限 QPS 就够了" | QPS 拦不住"一个请求带 10 万 token"；TPM / 并发数必须一起上 |
| "TPM 是每秒 token 数" | TPM = **Tokens Per Minute**；每秒的另有 RPS/QPS |
| "限流和配额是一回事" | 速率限制管**瞬时速率**，配额管**累计总量**，两个独立的桶 |

## 相关问题

- **为什么 DeepSeek / 讯飞的缓存命中要单独计价？** → 命中部分跳过 prefill，成本结构不同；价差可达 30 倍，记账时必须从 `prompt_tokens` 里减出去。
- **网关如何知道一次流式请求用了多少 token？** → 边收边累计，同时监控是否超过配额；这也是"必须边收边算"的原因。
- **JWT 和 API Key 能同时用吗？** → 常见做法：对外 API Key，内部服务间 JWT（无状态、可携权限）。
- **多实例网关的限流状态放哪？** → Redis（集中计数 / 令牌桶），或用一致性哈希把同一租户路由到同一实例。
